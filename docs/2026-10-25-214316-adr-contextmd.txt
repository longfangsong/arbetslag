❯ 我感觉 项目整体的 type 和 kind 用法也需要做一些限制                           

⏺ 我同意要立规矩。现在这两个词的含义已经有点交叉了,而且还会继续扩散:history
  的内容块、改图操作、隔离原因这些地方,都很可能顺手再用一次 type 或 kind。

  现状

  ┌─────────────────────┬─────┬────────────────────────────────────────────┐
  │        位置         │ 词  │                  实际含义                  │
  ├─────────────────────┼─────┼────────────────────────────────────────────┤
  │ Message.type、端口  │ typ │ 消息的类别(ADR-0005)                       │
  │ 名                  │ e   │                                            │
  ├─────────────────────┼─────┼────────────────────────────────────────────┤
  │ 触发器 kind         │ kin │ 事件源种类,要去宿主注册表里查实现(ADR-0001 │
  │                     │ d   │ )                                          │
  ├─────────────────────┼─────┼────────────────────────────────────────────┤
  │ effect 的 kind      │ kin │ 效果种类,同样要去注册表里查(ADR-0006)      │
  │                     │ d   │                                            │
  ├─────────────────────┼─────┼────────────────────────────────────────────┤
  │ 违规、隔离原因      │ cod │ 封闭枚举                                   │
  │                     │ e   │                                            │
  └─────────────────────┴─────┴────────────────────────────────────────────┘

  这里有两处冲突:

  - ADR-0004 已经明确废弃了"节点 kind"这个说法,所以 kind 不能再用在节点上。
  - 后面 agents 包的 history 内容块、改图操作等,如果都用 type 或 kind
    当判别字段,两个词就会彻底失去含义。

  建议的规则

  1. type 只表示消息类别。 只用于 Message.type、端口名,以及 messageType
     这类明确指"消息的类别"的复合名。
  2. kind 只表示宿主注册表里的键。 即 effect kind、trigger kind。它总是和一份
     schema 配对,并且总会带一个载荷字段(config 或 input)。
  3. 其它内部的判别联合,不用这两个词。 按领域选更具体的词:
     - 违规、隔离原因、错误,用 code(已经是这样)。
     - 改图操作,用 op,比如 { op: "spawn" }。
     - history 内容块,用 block,比如 { block: "text" }。
     - 其它情况再具体问。
  4. 新增一个注册表时,不另造名字。 沿用 kind,并且在 CONTEXT.md

❯ 为什么不直接把 kind 当 type

❯ 解释一下 ref 是干嘛的                                                         

⏺ ref 是节点给自己贴的认领标签,用来在回执回来时认出"这是我哪一次请求的结果"。

  为什么需要

  效果不是函数调用:节点交出请求后这条转移就结束了,state
  存盘,节点什么都不"等"。过一阵子,@effect.end
  作为一条普通消息进邮箱,节点要靠消息本身判断它对应哪次请求。

  内核给每个效果配了一个 effectId,但那是内核的幂等键,step 
  看不见(ADR-0006),所以节点不能用它。于是节点自己带一个
  ref,内核原样存下来,回执时原样还给它。

  一个例子

  agent 一次发两个效果:一个 model.complete,一个 timer.wait 当超时。

  交出:  { kind: "model.complete", input: {...}, ref: "turn-3" }
         { kind: "timer.wait",     input: {ms: 30000}, ref: "timeout-turn-3" }
  state: { waiting: ["turn-3", "timeout-turn-3"] }

  回执回来是两条 @effect.end,agent 看 ref:

  - "turn-3" → 模型答完了,继续处理。
  - "timeout-turn-3" → 超时了,先看 turn-3 是不是还在 waiting 里,在才处理。

  没有 ref 的话,两条回执长得一样,节点分不出谁是谁。ADR-0009 的 subagent
  超时竞态也是靠这个判断"这条回执还有没有意义"。

  关键点

  - 内核不解释 ref,它是 JSON,只原样带回。
  - 作者自己定格式,可选;不需要区分的节点可以不给。
  - 节点自己的 state 里要记"我在等哪些 ref",内核不代劳(ADR-0006 的代价之一)。
  - 效果记录和 ref 一起进快照的"在飞记录",回来就删。

  这里要定的事

  回执信封只有 from、type、body 三个字段,而 @effect.end 没有 from,所以 ref
  只能放进 body。但 body 的形状按效果种类各自声明(model.complete 的是 { ok, 
  message }),种类的 schema 里没有 ref 的位置。

  我的方案是内核把回执的 body 统一包一层:{ ref, result },result
  才是种类声明的形状。你觉得可以吗?

  改图建模成"特殊的 effect"

  我认真想了一遍,这样建模可以让 Transition 
  保持三个字段,但我建议不要这样做。原因是它会把"特殊"从 Transition 转移到 effect
  这个概念上,而且会破坏 ADR 里几条目前成立的保证。

  冲突的地方

  1. 原子性。 ADR-0009 的 subagent 要在一次转移里新增 child、接回边、把任务发给
     child。这要求改图和发消息在同一次提交里生效,而且 ADR-0002
     规定"消息发送在形状落定之后才解析"。真正的 effect
     是交给宿主的执行器、过一阵子才有回执的,做不到这一点。要让它同步生效,就只能
     让内核自己在这条转移里执行。
  2. "内核从不执行效果"。 ADR-0006 的核心立场是效果是数据,执行归宿主。改图由内核
     执行,就得开一个例外:内核认识一类"内建 kind",自己执行。
  3. "回执一定有"和"在飞记录"。 效果交出后进快照的在飞记录,回来一条
     @effect.end。同步执行的改图没有在飞记录,也没有回执,correlationId
     也毫无意义。
  4. 顺序。 ADR-0002 规定了固定顺序(先全量校验,再新增 → 接线 → 回收)。effects
     是个有序数组,内核得对其中的内建项另行排序,或者规定数组里的顺序有语义,两种都
     比一个独立字段更隐晦。

  我做的几个决定,请逐条确认

  1. 没有边的端口:无名边目前不参与路由。 发送总是带端口名,路由只按 (from, port)
     找边;无名边没有端口名可匹配,所以现在是惰性的。这是前面一直挂着的那个遗留问
     题,我选了最保守的解释。如果你想让无名边有用途(比如作为"该节点所有端口的兜底
     "),我们需要再定,否则也许应该直接从形状里禁掉无名边。
  2. 停住时的 graph.mutate:跳过。 停住的工作流里,执行器交来的 graph.mutate 返回
     skipped,不应用,记录保留,resume 之后恢复扫描会重新交出。理由是 ADR-0008 说停
     住期间内核拒绝推进,回执照收,但改图不是回执。你如果想让停住时也应用,告诉我。
  3. 没有 migrate 的版本落后:沿用旧 state,只做 schema 校验。
     通过就把版本号升上来,不通过停住。ADR-0004 说 migrate
     可选,但没说缺省怎么办。
  4. 快照超限只在 run 里检查,deliver 不检查。 超限的投递不会被拒绝,而是在下一次
     run 时停住。ADR-0008
     也承认回执可能撞限,这里的取舍是不让外部投递因为体积失败。
  5. 日志在落盘之后才写,写失败被吞掉。
     这样被冲突作废的那几次不会留下记录,日志也不会影响推进。

❯ 1. 这里的 无名边 什么时候会出现？                                             

⏺ 按现在的设计,没有任何地方会产生无名边。 只有当作者在模板或 connect
  操作里故意省略 port,它才会出现,而出现之后什么也不会用到它。

  为什么没有人产生或使用它

  - 发送总是带端口名。 ADR-0005 规定一条发送必须有一个端口,路由只按 (from, port)
    找边,所以无名边永远匹配不上。
  - 触发器出发的边必须带端口名。
    这一条是我在改触发器时加的,因为端口名就是投给节点的消息类别。
  - to 显式目标的发送不需要边。 我现在的实现里,to 绕过边直接投递。

  它是从哪来的

  ADR-0002 定义边是 { from, to, port? },并给无名边单独写了一条规则:(from, to)
  至多一条。CONTEXT.md 里端口的条目写着"端口只是给某条边一个名字,不改变这条路存
  不存在"。这些话背后的想法大概是:"边"表示 A 到 B
  的路存在,端口只是给这条路起的名字。无名边就是"有路但没名字"。

  这和后来定下的"消息类别 = 端口名"(ADR-0005)是不太一致的:一旦所有消息都带类别,
  没有名字的路就没有消息可以走了。

  唯一可能给它用途的地方

  CONTEXT.md 里还写着"节点之间的通信只能沿边走"。如果想让它成立,那么 to
  显式目标的发送也应该要求存在一条 (from, to) 
  的边,这时无名边就是"仅允许点对点发送"的授权,不带端口名。但我现在的实现里 to
  完全不检查边,所以这个规则并没有被执行。

  我的建议

  直接禁掉无名边:port 变成必填。

  - 边永远是 { from, to, port },一条边就是"某个出口接到某个目标"。
  - 去掉 (from, to) 至多一条的规则和对应的检查,edge_duplicate
    只剩完全重复这一种情况。
  - ADR-0002 里边的定义、CONTEXT.md
    里"边"和"端口"的条目、"端口只是给某条边一个名字"这句要改。
  - to
    显式目标的发送是否需要边,是另一个独立的问题,我建议保持现状:不需要。ADR-0005
    说它是"用于运行时新增的节点",而新节点刚创建时没有任何边,要求有边就失去了用途
    。CONTEXT.md 里"通信只能沿边走"那句要加上这个例外。

  另一个选择是保留无名边,并让它授权 to
  显式发送。但这会给运行时新增节点带来额外的"先接线"一步,我觉得不值得。

  你倾向哪个?确认后我一并改 ADR、CONTEXT.md 和代码。
