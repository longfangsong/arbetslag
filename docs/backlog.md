## 001 消息：单播 / 多播 / 广播

**状态**: 已定（→ `docs/adr/0011-edge-is-subscription.md`）

结论：边是**订阅**（`(from, port)` 可以有 0..N 条边，接了几个就是几条边），显式 `to` 是**寻址**。
不引入 topic / 订阅表 / 总线，也不引入 `mode: unicast | multicast`（边表已经是基数的唯一真源）。
原条目里「靠约定区分事实与指令」这条判断被 ADR-0011 否决（不要语义标签），「扇出需要中间节点」被推翻。
它对落盘量的影响不成立，所以 002 不再依赖它。

## 002 落盘粒度：整份快照

**状态**: 未定（先测量，再决定）

### 现状（代码事实）

- 每次改动都写**整份快照**：`SnapshotStore` 只有 `load` / `save` / `drop`（`packages/kernel/src/snapshotStore.ts`，48 行），一份工作流 = 一条记录。
- `fsStore.save` 还要把整份读回来做 CAS 比对（`readRecord` → `JSON.parse` → `snapshotSchema.parse`），再整份 `stringify` + 临时文件 + rename。**一次保存 ≈ 2 次整份解析 + 1 次整份序列化。**
- `advance` 每一步都 `structuredClone` 一次整份快照，再 `JSON.stringify` 一次算 `maxSnapshotBytes`；一个 8 步的 Run ≈ 10 次整份克隆 + 10 次整份序列化。
- **一轮对话的写次数**（`driveWorkflow` 的轮数 × 每次写）：无工具约 6 次（投递 1 + 每轮 `run` 1 + 每个回执 1 + 收尾 1），一次工具调用约 8 次。
- 快照里唯一无界增长的是 history；并且模型调用进行中它在 `inFlight[].input.messages` 里还有**第二份**（持久化的）。

### 三个候选

| 方案 | 收益 | 代价 |
|---|---|---|
| **A. 同一份快照内压缩/截断 history** | 同时降低写放大与 2 MB 上限 | 真丢原文（可保留滚动摘要）；`conversation` 今天只有 `user` / `append`，**没有"重写"语义**，压缩无处落脚 |
| **B. history 外置成 append-only 日志 + 快照存 watermark** | 写成本降到 O(增量)，2 MB 不再限制历史 | ADR-0003「单一事实来源」要改写成"快照 + 单调日志 + watermark"，顺序规则：先追加、后提交 watermark。安全性来自"追加是单调的，没有半追加这种不可达状态" |
| **C. 每节点独立记录** | 消除跨节点写放大与串行 | 放弃一致切面、exactly-once 出图、全局 FIFO、静止推导——见 003。等价于换架构（actor 风格） |

### 关键区分（容易搞错）

> **压缩「模型视图」不解决落盘问题。** 给模型一份压缩后的 history，`conversation.history` 的快照字节一个不少。

- 动机是模型上下文窗口 → 视图压缩就够（但视图不能是第二个持有者，见下）。
- 动机是 2 MB / 写放大 → 必须压**所有者里的那份原始日志**。
- 动机是"调用期间双份 history" → 是另一个问题（让 `input` 只放引用、Performer 调用时读日志），与粒度无关。

### 一个自相矛盾要先修掉

上一轮讨论里提过"另起一个 `context` 节点维护压缩视图"，那**违反 ADR-0010 自己的理由**（"每个消费者都要维护一份镜像，history 就有第二份真源"）。正确形态：

> **history 只有一个所有者；压缩不是"另一个节点存一份压缩副本"，而是"所有者内部的状态重写"。**

这反过来要求 `conversation`（或任何持有无界状态的定义）长出"重写"的能力，而不只是 `append`。

### 先做的事（不做决定之前）

给 `store.save` 加一条旁路日志：`(workflowId, bytes, steps, round, reason)`，用 `examples/basic-bot` 跑 20 轮，看三条曲线：快照字节随轮次、单轮写字节总量、history（含 `inFlight` 里那份）占比。

**测量必须在 001 之后做**，否则多播带来的份数增加会被低估。

判据：

- history 占比高 → 做 A，别动 B/C。
- `inFlight` 里那份占比高 → 先解决"调用期间双份 history"。
- 两者都不高 → 写放大来自**次数**不是**大小**，那该做的是 004 的合并写，而不是动粒度。

### 相关

- 001（多播会把 history 的份数乘上去）。
- 003（放弃整份快照到底放弃什么）。
- ADR-0003 的反转条件已提到「如果全量写成为瓶颈……『投递队列 + 游标』重新上桌」——那是**另一种**解法，与"分节点落盘"不是一回事。

## 003 持久化分档：不是所有状态都需要 ACID

**状态**: 未定

### 现状

现在对所有状态施加**同一档**保证：整份原子 + 每次变更立即落盘。但这档保证其实买了两样东西，只有一样是正确性：

- **买一（正确性）**：出图之前先记下意图。
- **买二（省钱）**：崩溃后不用重做已经算完的图内工作。

两样共用同一次 `save`，所以"算完一轮"就要付整份快照的钱。**第二样只是性能优化。**

### 分档依据：外部可见性

| 状态 | 丢了会怎样 | 真实需求 |
|---|---|---|
| **`inFlight`（出图意图）** | 外部动作可能已发生/未发生，工作流永远不知道 → 重复或丢失外部副作用 | **强持久，且在交给 Performer 之前**。唯一的 write-ahead |
| **入站投递**（触发器/webhook 进来的消息） | 用户说的话没了 | 强持久，**或**外部来源能重投 + 前端去重（Telegram 能，webhook 未必） |
| 形状（节点/边/触发器） | 图错了 | 强持久，但变更稀疏，成本可忽略 |
| `conversation.history` | 丢对话 | 只需要**单调**，天然可增量，不需要原子 |
| 节点 state（`pending` / `modelCall` / `seen`） | 等不到该等的、重复问一次模型 | **可重做**，不需要强持久 |
| 邮箱 | 消息丢 | 可由日志重放或重投重建 |
| `nextSeq` | 顺序变 | 只要单调即可 |
| 转移日志 | 少几条 | 旁路，已明确可丢 |

**只有第一行的丢失是外部可见的。** 其余丢失只影响"重做多少"和"状态微调"。

### 一个先决矛盾（ADR 之间打架）

> **已定（→ `docs/adr/0012-causal-order-only.md`）**：不是二选一。冲突来自把四种「确定性」混成一个词——
> 内核推导确定（承诺）、可重放（靠记录**输出**，不靠 step 确定）、语义确定（不可能）、分支时序（不需要）。
> 所以下面的 **(a) 让 step 真的确定** 作废（不该逼节点把时间从消息里取）；**(b) 记录转移的输出** 可行，
> 但它的动机是「少落盘 / 可回放」，与「重放确定性」无关，属于本条目剩下的部分，仍未定。

- **ADR-0003**：「step 是纯的、确定性的，所以一整段图内推进崩溃后可以原样重放。」
- **ADR-0004**：「『纯』指不产生副作用、不持有资源，**不承诺确定性**：`step` 可以读时钟与随机数。冲突重试会让同一条消息被处理两次，两次结果可能不同，以落盘那次为准。」

两条直接冲突。而「少落盘、崩了重放」**完全依赖前者**。今天之所以能容忍"冲突后丢掉内存推进重跑"，靠的是"重跑结果整份覆盖落盘"，不是"重放确定"。

必须二选一：

- **(a) 让 step 真的确定**：禁止时钟与随机，时间由触发器投递时盖进消息。代价：节点想"看现在几点"要靠外部事件带进来。
- **(b) 记录转移的「输出」而不是重新执行 step**：日志存 `sends` / `effects` / state diff，重放 = 重新应用输出（命令日志）。

选 (b) 看起来是回到 ADR-0003 retired 的「投递队列 + 游标」，但**那条 retired 的理由是"队列即邮箱会失去 FIFO 与静止推导"，纯 append 的日志不吃这条否**——日志 + 检查点仍能推导静止。这条 retired 可能一并否掉了不该否的东西。

### 不动真相模型就能省的两处

1. **丢掉「什么都没出」的那一轮的 `save`**。`advance` 里每个转移都把 `changed` 置真（哪怕只是 shift 邮箱 + `nextSeq` 自增），所以最后一轮（处理完最后一个回执、没有新效果、达到静止）纯粹为记录"回执被消费了"而写整份快照。那一轮没出图，丢弃这次写是安全的：重放它不产生任何外部动作。
   - 代价：**转移日志会与落盘真相不一致**（日志记了几条转移，重启后又重放一遍）。要么给这类日志打 `provisional`，要么接受"日志是尽力而为"。
   - 收益：一轮 8 次写 → 6–7 次。
2. **`submit` 里 `deliver` + `run` 合并成一次 CAS**（现在 `host.ts` 的 `submit` 是 `deliverToNode` 一次写 + `driveWorkflow` 再一次写）。省首轮那次写，并消掉"消息已落盘、图还没推进"的崩溃窗口。

**省不掉的是"每次写多大"**——那要动粒度（002）。

### 两条大路（要动真相模型时）

- **L1 日志为真相、快照为检查点**（Temporal / Akka 那一类）：每次推进 = 一次 append（O(1)），定期打检查点；恢复 = 检查点 + 重放后续日志。前提是先解掉上面那个矛盾。代价：ADR-0003 整条重写，且要专门测"检查点边界"这一类 bug。
- **L2 分档持久化**（节点自述"我的状态可重建"）：**不建议**。它把一个全局可证明的性质换成每个节点自述的、框架无法验证的性质；要给节点定义长出第 8 个字段（ADR-0004 的封闭字段清单正是为了拒绝这种扩展）；说谎的后果只在崩溃时暴露。现在也只有一个节点真的需要它（agent 的 `pending`）。

### 决策依据（三个外部事实）

1. **入站事件能不能重投？** 能（Telegram 靠 `update_id` 去重）→ 入站可以不那么强持久；不能（webhook、工作流之间互相投递）→ 必须强持久。
2. **重做一轮多贵？** 一次 LLM 调用几秒 + 花钱，那"少落盘多重放"是拿钱换 I/O。
3. **外部副作用重复多贵？** 发消息重复可忍，转账重复不可忍。这决定 `inFlight` 是否必须 write-ahead（现在已经是）。

一句话：**正确性只需要"出图前记账 + 入站不丢"两处，其余是拿 I/O 换重算的汇率问题。先把汇测算出来（002），再决定换不换。**

## 004 原子提交交给事务性存储，不再自造

**状态**: 未定（推荐先做，独立于 002/003）

### 现状

内核把"一次转移的所有改动原子生效"用 CAS + `revision` + 重试手写了一遍：

- `snapshotStore.ts`（48 行）定义 `Revision` 与 `Conflict`；
- `run/update.ts`（32 行）是重试循环（≤3 次，`MAX_ATTEMPTS`）；
- `hosts/node/src/fsStore.ts`（108 行）用"临时文件 + rename + 每次 save 整份读回来比对"实现它；
- `hosts/node/src/workflowIndex.ts`（41 行）+ `recovery.ts`（79 行）用扫目录回答"谁需要恢复"；
- `hosts/node/src/queue.ts`（44 行）用进程内 promise 链实现"串行入口"。

### 关键区分

| | 是什么 | 谁该负责 |
|---|---|---|
| **① 原子提交** | 一次转移（或一整段 Run）对快照的改动全生效或全不生效 | **不该自己写**。这就是 `BEGIN…COMMIT`，现在等于手写乐观并发控制 |
| **② 持久化执行** | 外部调用可能几秒/几分钟/永不返回；崩了要从"意图已记、结果未知"继续 | **没人能替你**。事务不可能开着锁等 LLM |

**② 是这套东西存在的理由，① 只是实现细节。** 感觉在"自造事务系统"，是因为把 ① 也自己写了。而 ② 现在用的已经是标准模式：

- `inFlight` = transactional outbox；
- `completeEffect` 的"删记录 + 追加回执同一次写" = outbox 的 ack（一次性令牌）；
- `at-least-once` + `effectId` 幂等 = outbox 的重投规则。

### 换成事务性存储，得到什么 / 得不到什么

| | |
|---|---|
| ✅ | CAS 变一行 SQL（`UPDATE … WHERE revision = $1`，受影响行数 0 = 冲突），`SnapshotStore` 仍是 3 个方法 |
| ✅ | `fsStore` 的临时文件 / rename / 整份读回比对全部消失 |
| ✅ | 跨进程串行化（`KeyedQueue` 只管进程内） |
| ✅ | 恢复扫描变成索引查询；`Store.list()` 的 ADR 顾虑在 DB 下不存在 |
| ✅ | 备份、复制、时间点恢复；`pg_column_size` 直接回答 002 的三条曲线 |
| ❌ | **不解决写放大**：还是整份 JSON 写一行，只是换成 `jsonb`。粒度问题（002）一点没变 |
| ❌ | 不解决"跨边界"：事务里绝不能放 Performer |
| ❌ | 不解决"谁来跑"：`driveWorkflow` 仍是宿主的活 |

### 一个部署问题决定这不是选型而是换平台

ADR-0003 拒绝 `Store.list()` 的理由是「一份工作流住在 Durable Object 里时，它永远列不出全库谁有 pending」。而现在的形状（一份工作流 = 一条记录 + 单写者 + 进程内按 id 串行）**看起来正是被 DO 语义塑形出来的**——DO storage 本身就是"事务性 KV + 单对象单写者"。

- 跑在 DO / Workers → 已经在用事务性存储，"自造事务"是文件系统实现造成的错觉，补一个 DO store（几十行）即可。
- 跑在 Node / 自有服务器 → SQLite 或 Postgres 是纯收益，`fsStore` 可以退役。
- 两个都要 → `SnapshotStore` 已经做到了，各写一份 adapter。

### 三个选项

- **T1（推荐先做）**：只把 ① 外包。一张表 `workflows(id, revision, snapshot jsonb)`，`save` = 带 `revision` 条件的 UPDATE，约 30 行。**语义一个字不变，不改任何 ADR**；删掉 `fsStore` 的大部分、`workflowIndex`、整份读回比对。它同时是 002 的测量平台。
- **T2**：连粒度也外包（节点状态/邮箱/outbox 各成一行），多节点改动用真事务，outbox 用 `FOR UPDATE SKIP LOCKED` 轮询，恢复是一条带索引的查询。**在 002 测出来之前不要做**；代价是 ADR-0003 重写 + 失去"整份快照可 dump / diff / 回放"（现在的调试与测试很大程度靠它）。
- **T3**：不自己做持久化执行，架在 Temporal / Restate / DBOS 上。会杀死项目前提（自己的图内核、`graph.mutate`、纯 step、可整份 dump 的快照），但最快拿到正确性与运维。诚实选项，不推荐。

### 两条纪律（换 DB 之后必须守住）

1. **事务只包「读快照 → 纯 step → 写回」，绝不包 Performer。** 有事务之后最常见的错误就是"反正有事务，把调用放进去更简单"——长事务 + 连接池耗尽，比现在的 CAS 重试难查一百倍。
2. **保留「每份工作流单写者」。** 即使有 `SERIALIZABLE`，跨节点写冲突重试的代价也远高于"同一份工作流串行"；`KeyedQueue` 换成 `FOR UPDATE` / advisory lock。**这不是自造事务，是降低冲突的设计。**

### 验收（T1 探针）

- 一个 `sqliteStore`（~30 行）实现 `SnapshotStore`，现有 `fsStore` 的测试克隆一份跑通。
- 跑通说明**内核与存储已经解耦**；跑不通的地方就是内核偷偷依赖文件系统语义的地方，那才是要先修的。
- 之后无论选 SQLite / Postgres / DO，都只是换 adapter。
