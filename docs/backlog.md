## 002 落盘粒度：整份快照

**状态**: 未定（先测量，再决定）

### 现状（代码事实）

- 每次改动都写**整份快照**：`SnapshotStore` 只有 `load` / `create` / `commit` / `drop`（`packages/kernel/src/snapshotStore.ts`），一份工作流 = 一条记录。
- 落盘是单文件 SQLite，一次推进 = 一条 `BEGIN IMMEDIATE … COMMIT` 里的一次 `UPDATE`（ADR-0013）。**写成本基线就建在这上面。**
- `advance` 每一步都 `structuredClone` 一次整份快照，再 `JSON.stringify` 一次算 `maxSnapshotBytes`；一个 8 步的 Run ≈ 10 次整份克隆 + 10 次整份序列化。
- **一轮对话的写次数**（`driveWorkflow` 的轮数 × 每次写）：无工具约 6 次（投递 1 + 每轮 `run` 1 + 每个回执 1 + 收尾 1），一次工具调用约 8 次。
- 快照里唯一无界增长的是 history；并且模型调用进行中它在 `inFlight[].input.messages` 里还有**第二份**（持久化的）。

### 三个候选

| 方案 | 收益 | 代价 |
|---|---|---|
| **A. 同一份快照内压缩/截断 history** | 同时降低写放大与 2 MB 上限 | 真丢原文（可保留滚动摘要）；`conversation` 今天只有 `user` / `append`，**没有"重写"语义**，压缩无处落脚 |
| **B. history 外置成 append-only 日志 + 快照存 watermark** | 写成本降到 O(增量)，2 MB 不再限制历史 | ADR-0003「单一事实来源」要改写成"快照 + 单调日志 + watermark"，顺序规则：先追加、后提交 watermark。安全性来自"追加是单调的，没有半追加这种不可达状态" |
| **C. 每节点独立记录** | 消除跨节点写放大与串行 | 放弃一致切面、exactly-once 出图、全局 FIFO、静止推导——见 003。等价于换架构（actor 风格） |

### 关键区分（容易搞错）

> **压缩「模型视图」不解决落盘问题。** 给模型一份压缩后的 history，`conversation.history` 的快照字节一个不少。

- 动机是模型上下文窗口 → 视图压缩就够（但视图不能是第二个持有者，见下）。
- 动机是 2 MB / 写放大 → 必须压**所有者里的那份原始日志**。
- 动机是"调用期间双份 history" → 是另一个问题（让 `input` 只放引用、Performer 调用时读日志），与粒度无关。

### 一个自相矛盾要先修掉

上一轮讨论里提过"另起一个 `context` 节点维护压缩视图"，那**违反 ADR-0010 自己的理由**（"每个消费者都要维护一份镜像，history 就有第二份真源"）。正确形态：

> **history 只有一个所有者；压缩不是"另一个节点存一份压缩副本"，而是"所有者内部的状态重写"。**

这反过来要求 `conversation`（或任何持有无界状态的定义）长出"重写"的能力，而不只是 `append`。

### 先做的事（不做决定之前）

给写入加一条旁路日志：`(workflowId, bytes, steps, round, reason)`，用 `examples/basic-bot` 跑 20 轮，看三条曲线：快照字节随轮次、单轮写字节总量、history（含 `inFlight` 里那份）占比。

测量的两个前置都清了：存储已换成 SQLite（ADR-0013），多播的份数规则已定（ADR-0011）。可以直接量。

判据：

- history 占比高 → 做 A，别动 B/C。
- `inFlight` 里那份占比高 → 先解决"调用期间双份 history"。
- 两者都不高 → 写放大来自**次数**不是**大小**，那该做的是把回执合并成一次写（`settleRound` 现在一条回执一次读写），而不是动粒度。

## 003 持久化分档：不是所有状态都需要 ACID

**状态**: 未定

### 现状

现在对所有状态施加**同一档**保证：整份原子 + 每次变更立即落盘。但这档保证其实买了两样东西，只有一样是正确性：

- **买一（正确性）**：出图之前先记下意图。
- **买二（省钱）**：崩溃后不用重做已经算完的图内工作。

两样共用同一次写，所以"算完一轮"就要付整份快照的钱。**第二样只是性能优化。**

### 分档依据：外部可见性

| 状态 | 丢了会怎样 | 真实需求 |
|---|---|---|
| **`inFlight`（出图意图）** | 外部动作可能已发生/未发生，工作流永远不知道 → 重复或丢失外部副作用 | **强持久，且在交给 Performer 之前**。唯一的 write-ahead |
| **入站投递**（触发器/webhook 进来的消息） | 用户说的话没了 | 强持久，**或**外部来源能重投 + 前端去重（Telegram 能，webhook 未必） |
| 形状（节点/边/触发器） | 图错了 | 强持久，但变更稀疏，成本可忽略 |
| `conversation.history` | 丢对话 | 只需要**单调**，天然可增量，不需要原子 |
| 节点 state（`pending` / `modelCall` / `seen`） | 等不到该等的、重复问一次模型 | **可重做**，不需要强持久 |
| 邮箱 | 消息丢 | 可由日志重放或重投重建 |
| `nextSeq` | 顺序变 | 只要单调即可 |
| 转移日志 | 少几条 | 旁路，已明确可丢 |

**只有第一行的丢失是外部可见的。** 其余丢失只影响"重做多少"和"状态微调"。

### 一个先决矛盾（已解）

> **已定（→ `docs/adr/0012-causal-order-only.md`）**：不是二选一。冲突来自把四种「确定性」混成一个词——
> 内核推导确定（承诺）、可重放（靠记录**输出**，不靠 step 确定）、语义确定（不可能）、分支时序（不需要）。
> 所以「让 step 真的确定」作废（不该逼节点把时间从消息里取）；「记录转移的输出」可行，
> 但它的动机变成「少落盘 / 可回放」，与「重放确定性」无关——那部分仍未定，就是下面的 L1。

「记录转移的输出」看起来像回到 ADR-0003 retired 的「投递队列 + 游标」，但**那条 retired 的理由是"队列即邮箱会失去 FIFO 与静止推导"，纯 append 的日志不吃这条否**——日志 + 检查点仍能推导静止。

### 不动真相模型就能省的两处

1. **丢掉「什么都没出」的那一轮的写**。`advance` 里每个转移都把 `changed` 置真（哪怕只是 shift 邮箱 + `nextSeq` 自增），所以最后一轮（处理完最后一个回执、没有新效果、达到静止）纯粹为记录"回执被消费了"而写整份快照。那一轮没出图，丢弃这次写是安全的：重放它不产生任何外部动作。
   - 代价：**转移日志会与落盘真相不一致**（日志记了几条转移，重启后又重放一遍）。要么给这类日志打 `provisional`，要么接受"日志是尽力而为"。
   - 收益：一轮 8 次写 → 6–7 次。
2. **`submit` 里 `deliver` + `run` 合并成一次 `commit`**（现在 `host.ts` 的 `submit` 是 `deliverToNode` 一次事务 + `driveWorkflow` 再一次事务）。省首轮那次写，并消掉"消息已落盘、图还没推进"的崩溃窗口。

**省不掉的是"每次写多大"**——那要动粒度（002）。

### 两条大路（要动真相模型时）

- **L1 日志为真相、快照为检查点**（Temporal / Akka 那一类）：每次推进 = 一次 append（O(1)），定期打检查点；恢复 = 检查点 + 重放后续日志。代价：ADR-0003 整条重写，且要专门测"检查点边界"这一类 bug。
- **L2 分档持久化**（节点自述"我的状态可重建"）：**不建议**。它把一个全局可证明的性质换成每个节点自述的、框架无法验证的性质；要给节点定义长出第 8 个字段（ADR-0004 的封闭字段清单正是为了拒绝这种扩展）；说谎的后果只在崩溃时暴露。现在也只有一个节点真的需要它（agent 的 `pending`）。

### 决策依据（三个外部事实）

1. **入站事件能不能重投？** 能（Telegram 靠 `update_id` 去重）→ 入站可以不那么强持久；不能（webhook、工作流之间互相投递）→ 必须强持久。
2. **重做一轮多贵？** 一次 LLM 调用几秒 + 花钱，那"少落盘多重放"是拿钱换 I/O。
3. **外部副作用重复多贵？** 发消息重复可忍，转账重复不可忍。这决定 `inFlight` 是否必须 write-ahead（现在已经是）。

一句话：**正确性只需要"出图前记账 + 入站不丢"两处，其余是拿 I/O 换重算的汇率问题。先把汇测算出来（002），再决定换不换。**
