# 部署配置：一个进程的资源写在 YAML 里，图仍在快照里

一个 bot 要跑起来，除了图，还要有：注册了哪些积木、模型端点在哪、拿哪个 token 听哪个 bot、状态存在哪个文件、开不开监控。这些都是**这个进程**的事，不是任何一份工作流的事。部署配置就是把它们从手写的 `main.ts` 搬进一份 YAML；图怎么长、怎么变，仍然只在快照里（ADR-0002、0003）。

**Status**: accepted（2026-11-06）

## 决定

### 部署配置负责什么

一份 YAML（`arbetslag run <file>` 读它），只描述这个进程的资源：

| 段 | 内容 |
|---|---|
| `store` | SQLite 文件路径 |
| `templates` | 模板目录 |
| `modules` | 本地模块（可选）；内置模块不用列 |
| `providers` | 带名字的模型端点：种类、base URL、key |
| `listeners` | 监听器列表：id、种类、监听器 config，以及它的密钥 |
| `host` | 轮数上限、重试间隔、Performer 时限（含按种类覆盖） |
| `monitor` | 开不开、端口、绑定地址 |
| `log` | 转移日志写到哪 |

相对路径相对配置文件所在的目录。

- **内置模块全部注册**：`@arbetslag/llm` 的节点与 `model.complete`，`@arbetslag/host-node` 的触发器种类、匹配函数、`timer.wait`、`telegram.send` 与通用节点（总机、Telegram 中继）。注册一个种类很便宜；没配 Performer 的效果只报告 `MissingPerformer`、不停住，部署补上之后再交出（ADR-0006）。内置模块里有重依赖的（比如要起浏览器的工具），在 Performer 第一次执行时才加载它，不拖慢启动。
- **本地模块**按路径列在 `modules` 里，`export default` 节点定义、效果种类、触发器种类、匹配函数，以及它们的 Performer 与监听器实现。这是"配置之外唯一要写代码的地方"。
- **密钥只以 `${ENV}` 出现**：启动时从环境变量解析，缺一个就不启动。密钥的值不进配置文件，更不进模板或快照。
- **启动前全量校验，失败就不启动**：配置的 schema、引用的 env、本地模块能加载、名字不重复，以及模板目录里每份模板按默认参数试实例化一遍（不落盘）。

### 按名字选，密钥留在部署里

工作流能配的东西写在节点 config 里，进快照；不能进快照的（密钥、端点）写在部署配置里，节点 config 只写它的名字。

- **模型**：`providers: { local: { kind: openai, baseURL, apiKey } }`；`llm` 节点 config 写 `provider: local` 与 `model`。`provider` 随 `model.complete` 的 input 交给 Performer，由它挑端点。省略时：部署里恰好一个 provider 就用它，否则回执失败。
- **监听器**：一个 token 一个监听器（ADR-0015 不变）。一个部署跑多个 bot 就是列多个监听器，工作流的触发器按 `listener` 选订阅哪一个。
- **发回 Telegram**：`telegram.send` 的 input 带 `listener`（是哪个 bot），Performer 按监听器 id 找它的 token。

### 模板目录

- 一个目录，里面每个 `.json` / `.yaml` / `.yml` 文件是一份模板；**文件名去掉扩展名就是模板名**。同名不同扩展名是配置错误。
- 模板可以声明**参数**：`params: { chatId: 0 }`，值是默认值。模板里任何字符串值写 `{{chatId}}` 即引用它：
  - 整个字符串就是一个占位符 → 换成参数值本身（数字仍是数字）；
  - 嵌在字符串里 → 换成参数值的文本（只允许字符串、数字、布尔）。
  - 引用了没声明的参数、或传了没声明的参数，都是错误。
- 填参数是内核导出的一个纯函数（`fillTemplate`），由宿主调用；它只做替换，不求值。
- 启动校验用默认值填一遍再试实例化，所以默认值要能让模板合法。

### `workflow.spawn` 按名字引用模板

- input 从"内联整份模板"改为 `{ id, template: <模板名>, params?, forward? }`（修订 ADR-0015 的 `workflow.spawn` 一节）。
- 宿主在**执行 spawn 的那一刻**按名字从模板目录取模板、填参数、实例化。名字不存在、参数不合、模板不合规 → 回执失败，不停住。
- 改了模板文件，之后新 spawn 的工作流用新版本；已经存在的工作流不受影响（ADR-0002：实例化之后快照才是事实来源）。
- 总机是 `@arbetslag/host-node` 里的一个通用节点（`switchboard`），config 写模板名、参数从载荷的哪个字段取、转交给新工作流的哪个触发器。它收到一条事件就交出一次 `workflow.spawn`。
- 新工作流的 id 是模板名与各参数值用 `:` 连起来（`chat:bot-a:42`），不是样式字符串：总机自己也从模板实例化，样式里的 `{{…}}` 会被当成总机模板的参数先填掉，要么报"未声明"，要么得再发明一套转义。

### 不在开机时创建工作流

部署配置不碰快照：它不声明"开机时要有哪些工作流"。工作流一律经监控（或调用 `host.create` 的代码）创建，之后住在存储里。新部署起来时没有任何工作流，这是预期的。

### 监控随之扩展（ADR-0017 的协议）

- `GET /api/templates`：模板目录里每份模板的名字、参数默认值与内容。
- `POST /api/workflows` 接受 `{ template: <名字>, params?, id? }`（从目录选），也仍接受上传的整份模板（JSON 或 YAML，由前端解析成对象）。

### 不负责什么

- **不放代码、不写表达式**：没有 `eval`、没有条件、没有字符串求值；占位符替换是唯一的"变换"。要新行为就写本地模块。理由同 ADR-0015 不存匹配函数代码。
- **不热加载**：改配置、改本地模块都要重启；重启就是换一个激活，由恢复扫描接上（ADR-0014）。模板目录例外：spawn 每次都读当前目录，但目录在启动时载入，改了文件也要重启才看得到。
- **不跨宿主**：只有 Node 宿主的加载器。Workers 的部署形态（`wrangler.toml`、DO 绑定）不同，到时候再看能共享多少（同 ADR-0017 不先抽数据源接口）。

## 为什么

- **为什么部署配置不建工作流**：工作流的来源是快照，创建是一次性动作。把"开机时确保存在"写进配置，读者会以为改配置能改正在跑的图；而它只在不存在时生效，改了也白改。
- **为什么 spawn 改成按名字**：内联的模板只能由节点的代码拼出来（`chatTemplate(chatId)` 是个 JS 函数），于是总机只能是每个应用各写一遍的代码。按名字引用之后，总机的 config 是纯数据，模板是目录里的文件，两者都不用写代码。
- **为什么参数要在模板里声明**：不声明，启动时就没法校验带占位符的模板（`"{{chatId}}"` 不是数字，`chatIs` 的 config 不合法）。声明了默认值，启动校验与监控上的"从目录创建"都有了现成的值。
- **为什么不让工作流自己配监听器**：一个外部事件源只能有一路监听（ADR-0015 的 Retired designs）。多个 bot 就是多个监听器，工作流在触发器里选。
- **为什么内置模块全注册**：显式列出只防住两件事——启动太慢、注册了没实现——前者靠延迟加载、后者本来就不停住。

## 代价（接受）

- **总机的行为依赖部署里的目录**：同一份快照换一个部署，spawn 出的工作流可能不同；目录里删掉模板，spawn 回执失败。
- **模板的默认值必须是合法值**：只为校验而存在的默认值（如 `chatId: 0`）会出现在监控的创建表单里。
- **新增 bot 要改配置并重启**：监听器是静态列表。
- **YAML 的坑**（`no` 读成布尔、缩进）由 schema 校验兜住，报错指到字段。

## 反转条件

- **要在不重启的情况下加载自定义节点**（已知的未来需求）：把本地模块的加载做成运行时可重载，重点是注册表要能换版本，正在跑的工作流按 ADR-0004 的版本与迁移处理。届时新 ADR。
- **加 bot 不想重启**：监听器按需起——部署只列密钥，触发器引用密钥名，宿主按"种类 + 密钥名"去重后起监听。要改 ADR-0015 与对账。
- **模板需要条件或循环**：不在配置里加表达式；写一个能生成图的节点（改图是效果，ADR-0002）。

## Retired designs（不要重提）

- **显式列出要用的内置模块**。
- **开机时确保某些工作流存在**。
- **模板是单个文件、内联在配置里**。
- **监听器由每份工作流自己配置**（含密钥）。
- **TypeScript 配置文件**：那已经是写代码。

## 验收

1. **配置即部署**：一份 YAML + 一个模板目录（总机、会话两份模板），不写一行 TypeScript，`arbetslag run` 起来之后，经监控从目录创建总机；对一个假的 Telegram 发两条不同 chat 的消息 → 两份会话工作流，各自经假的模型回话到各自的 chat。
2. **多个 bot**：两个 Telegram 监听器各有 token；回话经 `telegram.send` 用的是消息来源那个 bot 的 token。
3. **启动校验**：缺一个 env、模板引用未注册的节点、模板引用了未声明的参数、同名的 `.json` 与 `.yaml` → 不启动，报错指出哪一项。
4. **spawn 按名字**：名字不存在 → 回执失败，总机不停住；改了模板文件并重启 → 新 spawn 的用新版本，旧的不变。
5. **密钥不进快照**：跑完之后整个存储里搜不到任何一个 token 或 API key。
