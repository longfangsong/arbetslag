# 边界只有触发器：内核一个动词，触发器是形状里的一条入边

内核只提供 `run(workflow)`。向一份工作流投一条消息，就是一次带版本校验的写（消息进目标节点的邮箱）加一次 `run`。图外的一切事件源——webhook、轮询、cron、命令行——都是 store 与 `run` 的客户端；其中工作流声明在形状里的那部分是**触发器**：工作流自己持有的一份声明，"用 kind K、配置 C，把外部事件以类别 T 投给我的节点 N"。宿主只提供各个 kind 的实现，并按快照里当前声明的内容去建、改、拆真正的监听。内核存声明、校验声明，但从不执行触发器。

**Status**: accepted

## 决定

- **内核只有 `run`，没有 `dispatch`**。投递和图内节点的 `sends` 是同一个操作：消息进目标节点的邮箱。外部来的消息唯一的区别是没有发件人。
- **入口不是节点**。按节点的定义（有邮箱、有私有状态、只在收到消息时推进），入口三条都不满足。所以没有"入口节点"，也没有输入信封 `Event`；图内只有一种信封：**消息**。
- **触发器 = 形状里一条从图外指向节点的入边**：`{ id, kind, config, to, type }`。形状的第三类成员（节点、边、触发器），随快照持久。它不是节点：没有邮箱、没有私有状态、不会被推进。
- **`type` 是触发器投出的消息类别**，与边的端口名同构（ADR-0005）：节点按它分派。
- **来源是快照，不是模板**：模板里的 `triggers:` 只是实例化时的初始值，之后工作流与模板无关（ADR-0002）。
- **图可以改它**：增删触发器与 spawn / connect / retire 同类，共用"先全量校验、再应用"的改图流程。回收节点连带删除指向它的触发器，与删边同一条规则。
- **内核认识 kind 的名字与 config schema，不认识它的行为**：宿主把触发器 kind 的定义注入给内核，与节点定义同属一张注册表。
- **声明不合法 → 隔离**：未知 kind、config 不符合 schema、`to` 指向不存在的节点，在实例化、改图转移、载入时一律按"改图非法"处理（ADR-0008）。宁可停住，也不静默丢掉入口。
- **声明合法但起不来 → 不隔离**：端口被占、token 被拒、网络不通是外界的暂时状况。宿主把这条触发器记为未就绪，重试并报告，工作流继续运行。
- **对账归宿主，内核不推送**：每次 `run` 落盘之后，宿主把快照里的触发器声明与当前在跑的监听对比，多了就起、少了就停、变了就重建（与 ADR-0003 同一立场）。
- **图外投递没有 `from`，也不经过边。**
- **没有"切分"概念**：触发器属于某一份工作流，事件天然只投给它。"一个 chat 一份工作流"由一份持有触发器的"总机"工作流在节点里实现：收到消息后发一条跨工作流投递的 effect，宿主的执行器负责载入、必要时实例化、投递、`run`。内核不提供 get-or-create。

## 为什么

- **为什么没有 `dispatch` 动词**：单设一个，等于让内核假装知道"外部存在"。
- **为什么触发器不是宿主级**：它的出现、消失、改配置本来就是工作流行为的一部分（某个节点决定"从现在起监听这个源"）。活在宿主配置里，图无法改它，快照也说不清"这份工作流现在对外开着哪些入口"。
- **为什么是入边而不是新机制**：与边在生命周期、连带回收、改图校验上完全重合，复用同一套规则。
- **为什么内核认 schema 不认行为**：校验 config 是纯检查，与 state schema 同类；执行必须留在宿主，因为 Node / Workers 的监听方式根本不同（ADR-0003 的教训：不要用统一接口掩盖平台分叉）。
- **为什么起不来不隔离**：隔离是"内核拒绝再推进"，而且要人工解除；端口冲突这类暂时故障不该要人。

## 代价（接受）

- 一个 bot 一个轮询、webhook 去重、游标、重试——全是触发器实现方（宿主）的责任，框架不保证。
- 每个宿主都要实现对账：读快照、diff、起停监听。触发器 kind 注册表是宿主与内核之间的又一份契约，其 schema 改动同样会遇到迁移问题（留待后议）。
- 总机工作流是一份特殊的常驻约定：它持有 bot 级的触发器，必须先于任何 chat 工作流存在，由应用在引导时创建。

## Retired designs（不要重提）

- **入口节点 + `Event` 信封**：入口不满足节点的定义。
- **内核持有的路由表 `key → workflowId`**：它是调用方的一张表。
- **`dispatch` 作为内核动词**：投递是写，不是语义。
- **`forward` 结构字段**：跨工作流不是结构操作，见 ADR-0002。
- **模板里的 `channels:` 绑定 + `per:` 切分，以及触发器声明里的 `workflow: { id }` 切分规则**。
- **宿主级触发器 / 宿主启动时读模板的 `triggers:`**；**模板声明触发器名字、宿主另配绑定**。
- **内核对触发器 kind 一无所知**：至少要认名字与 config schema，才能在载入时隔离非法声明。
- **宿主可写入的隔离状态**：隔离仍然只表示内核拒绝推进。

## 反转条件

- 如果每个调用方（或每个宿主的对账代码）都在重复实现同样的路由、去重、游标，就把它做成随框架发布的 app / 库（`arbetslag serve`），而不是把入口搬回内核。
- 如果"声明合法但起不来"在实践中常需要人为介入，重新讨论是否引入"未就绪"的持久标记。
