# 一份工作流同一时刻只有一个激活：串行入口是契约

存储的事务只保证"不丢更新"（ADR-0013），保证不了"同一个在飞效果只被交出一次"。两段代码同时推同一份工作流，各自载入快照、各自看见同一条 `inFlight`，就会各自把它交给 **Performer**：模型被问两次，消息被发两遍。图上仍然 exactly-once（回执是一次性令牌，ADR-0006），但对外部世界的 at-least-once 从"只在崩溃时发生"变成了"并发时常态发生"。所以串行入口不能只是推荐。它要上升为宿主契约：**一份工作流同一时刻只有一个激活**，而且只有激活能把效果交出去。

**Status**: accepted

## 决定

- **激活 (Activation)**：宿主里对一份工作流负责的**那一个**活的执行上下文。所有对这份工作流的 `commit`（投递、`run`、落回执、`graph.mutate`）都在它里面发生，在飞效果也只由它交出去。
  - **Node**：持有存储文件的那个进程，对文件里的每份工作流都是激活。
  - **Workers**：那份工作流的 Durable Object 实例。
- **宿主契约 C1（单激活）**：同一份工作流在同一时刻至多一个激活。由宿主保证，内核不知情。
- **宿主契约 C2（交出至多一次）**：在一个激活的生命期内，每个 `effectId` 至多交给 Performer 一次。激活在内存里维护一个**正在执行**集合。有 C1，这个集合就足够了，不需要持久化的认领。
- **重复只来自换激活**：激活启动时（进程启动、DO 被唤醒）集合是空的，于是快照里**全部**在飞效果各交出一次。这是效果被重复交出的唯一来源（ADR-0003）。之后同一激活里的任何推进都只交出**新增**的在飞记录，不重扫整个 `inFlight`。
- **串行的范围只有 `commit`，不跨 Performer 的 `await`**：
  - 串行入口排队的单位是一次同步的存储事务（投递、`run`、落回执、`graph.mutate`），不是整段"推到静止"。
  - Performer 在串行入口**之外**执行。它返回之后，"落回执 + `run`"作为一项新的工作排回串行入口。
  - 所以模型在思考的时候，新到的用户消息照常投递、照常 `run`，不必等那几秒。
- **Performer 必须有超时**：超时由宿主计，到点就当作失败结果落回执（失败是结果，ADR-0006），并从"正在执行"集合里删掉。否则一个永不返回的 Performer 会让那条记录在这个激活里永远不被重交，又永远回不来。
- **停住期间**：已经交出去的效果照常回来、照常落回执（ADR-0008）；不交出新的效果。`resume` 之后由激活把留在快照里、且不在"正在执行"集合里的在飞记录交出去。
- **Node 上靠存储文件强制 C1**：进程打开存储文件时取得**独占锁**，并且在整个生命期内一直持有（SQLite 的 `locking_mode = EXCLUSIVE`）。第二个进程打开同一个文件会**启动即失败**，报出清晰的错误，不静默降级。一个文件只有一个进程。
- **Workers 上靠平台保证 C1**：同一个 id 的 DO 至多一个活实例。进行中的出站 I/O（包括 Performer 的 `fetch`）会阻止实例被驱逐，但每个操作最多 15 分钟；所以 **Performer 超时必须小于 15 分钟**，否则实例可能在等待中被驱逐，等于换了激活。
- **`effectId` 仍是 Performer 对外的幂等键**：换激活造成的重复由它兜住。在乎重复的 Performer（转账、发信）把 `(workflowId, effectId)` 传给外部系统的幂等接口。ADR-0016 起 `effectId` 由快照决定（`<seq>.<下标>`），所以崩溃后从检查点重放产生的重复也由它兜住。

## 为什么

- **为什么事务不够**：事务保护的是"读、算、写"这一段，而交出效果发生在提交**之后**、Performer 返回**之前**。这一段没有任何一次写可以挂靠。今天的 Node 宿主没出事，是因为 `submit` 把整段 `drive`（包括 Performer 的 `await`）都包在了 `KeyedQueue` 里，而这正是下一条要拆掉的东西。
- **为什么不把整段 drive 串行**：那样一次三秒的模型调用会把同一份工作流的所有投递挡住三秒。这与 ADR-0003 拒绝「Run 内 `await` effect」是同一个理由，只是挪到了宿主一层。
- **为什么认领放在内存，而不是持久化（`claimedBy` / 租约）**：持久化的认领必须回答"认领者死了怎么办"，而唯一不靠计时的答案就是"换激活了"。租约要选时长：太短，慢模型会被别人重领；太长，崩溃后要干等。有了 C1，"激活重启"本身就是一个精确、免计时的信号：此前的认领全部作废。认领的有效期就等于激活的生命期，不需要单独记录。
- **为什么 Node 要强制、而且启动即失败**：零配置自托管意味着用户一定会不小心起两个进程（开两个终端、`tsx watch` 重启时新旧重叠）。两个进程共享一个文件，正确性仍然由事务保证，但效果会被**常态地**重复执行，而且没有任何报错。启动时报一条明确的错误，比悄悄多发一倍的消息好得多。
- **为什么是 `locking_mode = EXCLUSIVE`，而不是锁文件或 pid 文件**：锁跟着 SQLite 连接走，进程崩溃时由操作系统释放，不会留下死锁文件。ADR-0013 拒绝"应用层跨进程锁"，理由正是它的崩溃处理更差。
- **为什么"正在执行"集合不进快照**：它描述的是激活的状态，不是工作流的状态。写进快照，下一个激活读到的就是一份别人的、已经作废的认领。

## 代价（接受）

- **Node 不能滚动部署**：新进程必须等旧进程退出才能启动，中间有一段空档。空档内到达的外部事件要靠来源自己重投（Telegram 的长轮询有 offset，不会丢；一般的 webhook 未必）。
- **Node 上没有部署重叠**：新旧进程不能同时在线。Workers 上新旧代码版本会重叠，但同一份工作流的 DO 只有一个实例。
- **Performer 超时是一个要调的数**：太短，会把慢但正常的模型调用判成失败；太长，会拖住一个本该早点重试的回合。宿主给默认值，并允许按效果种类配置。
- **Workers 上，等模型的时间就是 DO 的计费时长**：DO 按墙钟时间、以 128 MB 计 GB-s，等待出站 I/O 期间照样计费。量级：一次 10 秒的模型调用约 1.25 GB-s，按 $12.50 / 百万 GB-s 约 $0.000016；一百万次约 $16，远小于这些模型调用本身的费用。等待期间实例仍能处理别的请求（I/O 期间可交错），所以这不是吞吐问题。
- **一个激活内的交出是"至多一次"，所以 Performer 抛错和超时都必须落成失败回执**，不能"再交一次试试"。重试是节点的事：节点看到失败回执，自己决定要不要再交一个新的效果（ADR-0009）。

## Retired designs（不要重提）

- **串行入口只是"强烈推荐"**（ADR-0003 的那一节）。
- **整段 `drive`（包括 Performer 的 `await`）持有串行入口**：今天 `host.ts` 里 `submit` 的写法。
- **每次 `drive` 开头重扫并交出全部 `inFlight`**：今天 `executor.ts` 里 `driveWorkflow` 的第一步。只有激活启动时才这样做。
- **持久化的效果认领 / 租约**（`claimedBy`、`leaseUntil`、心跳）。
- **多个进程共享一个 SQLite 存储文件**。
- **锁文件 / pid 文件**来保证单进程。
- **靠存储事务防止效果被重复执行**。
- **"正在执行"集合写进快照**。

## 反转条件

- 如果 Node 需要零停机部署：把"启动即失败"改成"启动后等锁，并在等待期间持续告警"，让新进程在旧进程退出的那一刻接手。C1 不变。
- 如果某个目标平台给不出"每个 key 一个实例"：那个平台的宿主只能退回持久化认领 + 租约，并在文档里写明重复窗口的大小。契约本身（C1、C2）不变，变的只是那个平台对它的兑现方式。
- 如果"在 DO 里等"变得不划算（单次等待远长于模型调用、或 DO 时长费用接近效果本身的费用）：把 Performer 挪到 DO 之外（Queues 的消费者，按 CPU 计费，等待不计费），回执由消费者投回 DO。DO 一旦能休眠，内存里的"正在执行"集合就会丢，C2 只能靠**持久化的派发记录 + 截止时间**兑现：截止时间就是 Performer 超时（不是新的旋钮），到点由 alarm 落失败回执，迟到的结果因在飞记录已删而被丢弃。届时需要新 ADR。

## 验收

1. **Node 单进程**：起两个进程打开同一个存储文件，第二个在启动时失败，错误信息说明文件被另一个进程持有。用真实的子进程测，不 mock。
2. **模型思考时新消息不被挡**：Performer 卡在一个不 resolve 的 promise 上时，投递一条新消息，`run` 照常推进；那份工作流的转移日志里能看到新消息被处理。
3. **同一激活内不重复交出**：Performer 卡住期间连续投递 N 条消息、触发 N 次推进，Performer 对该 `effectId` 的调用计数始终是 1。
4. **换激活重交恰好一次**：关闭宿主、在同一个文件上新建宿主，卡住的那个 `effectId` 再被交出一次，计数变为 2，之后不再增长。
5. **超时落失败回执**：Performer 超时之后，节点收到 `{ ok: false, … }` 的 `@effect.end`，`inFlight` 里那一条被删掉。
6. **文档**：`CONTEXT.md` 新增术语「激活」，改写「串行入口」；`packages/hosts/node/src/queue.ts` 的注释与本 ADR 一致（不提 CAS / `Conflict`）。
