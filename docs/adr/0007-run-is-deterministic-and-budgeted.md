# Run 是确定的、有预算的

Run 从一次投递（或恢复）开始，反复取出入队最早的那条消息、让它的目标节点做一次转移，直到所有邮箱为空，或步数预算用完。顺序由内核保证确定；预算耗尽不是故障，Run 在那里停下并落盘，宿主再调一次 `run` 接着推。

**Status**: accepted；其中「顺序由内核保证确定」的精确范围、顺序规格与「哪些顺序不承诺」见 **ADR-0012**（本 ADR 的决定不变）。

## 决定

- **同一邮箱内按到达顺序处理；跨邮箱按消息入队的全局序号取最早的那条**（全局 FIFO）。顺序由内核保证，不依赖遍历顺序。
- **入队序号进快照，不进信封**：信封仍只有三个字段（ADR-0005），序号是内核对邮箱的簿记。
- **每次 Run 有步数预算**，防活锁。
- **预算耗尽不停住**：Run 在当前转移之后停下，落盘，结果带一个"因预算停下"的标记，此时邮箱可能仍非空。宿主据此决定再跑一次，或在连续 N 次耗尽后自行停住、报警。
- **静止是推导**（所有邮箱为空），不是状态；"Run 结束"与"静止"不再等价：Run 可能因静止而结束，也可能因预算而结束。
- **`awaiting` 取消**：节点不向内核声明"我在等谁"。等待只是节点自己状态里的一条记录加邮箱空着；要防"等的对象没了"，靠超时 effect。没有 `@await.broken`。
- **内核无法区分正常静止与死锁**：两者形状相同。只能靠节点显式记录、超时 effect 与观测让它"看得见"。

## 为什么

- **为什么要确定顺序**：转移日志要能与快照对应（**理由已由 ADR-0012 修正**：顺序的意义是因果闭合与可复现，不是"支撑确定性重放"）；若顺序取决于哪个节点先被遍历到，同一份快照加同一条投递可能得到不同的日志与不同的悬垂态，重试、排查、验收就都失去定义。
- **为什么序号放在内核簿记里**：顺序是内核的事，不是消息的属性；放进信封就多了一个应用可以读、可以伪造的字段。
- **为什么预算耗尽不停住**：agent → 工具 → agent 的循环可能合法地很长；把它判成 bug 会误伤。Run 本来就是幂等可续的（ADR-0003 的两个存盘点），续跑天然成立；真正的死循环由宿主看到连续耗尽来发现。
- **为什么取消 `awaiting`**：它要求内核替节点维护等待注册表，并在回收时投递特殊消息；这与"没有 supervisor、节点平等"（ADR-0002）相冲突，而且 `@await.broken` 只在"别的节点回收了我等的对象"时才有意义，这件事节点自己可以靠超时兜住。

## 代价（接受）

- 内核要维护一个单调递增的入队序号，随快照持久。
- 宿主要处理"因预算停下"的结果：再调 `run`，并自己决定何时放弃。
- 并行 spawn N 个子节点时，父节点要自己在 state 里数回执；没有内核帮它数。

## Retired designs（不要重提）

- **`awaiting` 作为转移字段、等待注册表、`@await.broken`**。
- **预算耗尽即停住**。
- **遍历顺序未定义**（"内核不保证"）。
- **"Run 结束 = 静止"**。

## 反转条件

- 如果并行等待子节点成为常态且节点实现反复出错，`awaiting` 可以以 agents 包 helper 的形式回来，而不是回到内核。
- 如果全局序号在多节点工作流里成为瓶颈或快照体积负担，再讨论放宽为每邮箱序号加确定性的轮转顺序。
