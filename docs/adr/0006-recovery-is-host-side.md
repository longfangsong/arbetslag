# 恢复扫描归宿主，Store 不加 `list()`

内核只定义"什么叫需要恢复"并保证 `run` 幂等；"谁去扫"由宿主实现。需要宿主处理的情况有两种：`status === active` 且邮箱非空（该跑一次 Run），或者有在飞 effect（该把同一个 `effectId` 重新交给执行器）。`Store` 保持 `load` / `save` / `drop` 三件。

**Status**: accepted

## 为什么

- **`list()` 在目标平台上语义不成立**。若一个工作流落在一个 Durable Object 里，那个 DO 只能列出自己的存储，永远列不出"全库哪些工作流有 pending"。把 `list()` 写进 `Store`，就是在定义一个只有一半实现能兑现的接口。
- **恢复契约不能靠同名接口掩盖分叉**。Node 上恢复是"扫目录"，Workers 上是"调用方自己的索引 + 每个工作流的 alarm"。这两件事形状不同，用一个假的统一接口包起来，只会让两边都以为自己已经实现了恢复。
- **内核提供的东西已经够用**：一个判定、一个幂等的 `run`、一个 `Conflict`。剩下的是宿主的十行代码。

## 代价

- 每个宿主都要自己实现"谁需要跑"。Node 上约十行；Workers 上要自带索引（KV / D1）或依赖 alarm，等于把一部分可靠性外包给部署方。
- 没有"全局待办视图"这个内核能力。运维要看积压，只能看宿主自己的索引。

## 强烈推荐（不是契约）

宿主为同一工作流提供串行入口，并且恢复扫描要能捡起"投递成功、Run 没跑"的悬挂态。这两件事都是宿主的责任，内核只能用 `Conflict` 和积压来指出它们没做好。

## Retired designs（不要重提）

- **`Store.list()`**：见"为什么"第一条。
- **内核在启动时扫全库**：内核没有启动这回事，它没有常驻进程。

## 反转条件

如果每个宿主都在重复写同样的索引与游标，并且都写错过一次，那就把它做成随框架发布的 app（`arbetslag serve`），或者定义一个可选的 index 协作者接口——而不是把 `list()` 塞回 `Store`。
