# 工作流就是它那条快照，恢复归宿主

一份工作流在任一时刻就是 store 里的一条快照记录。内核没有跨 Run 的常驻内存态：推进 = 在存储的一次事务里载入快照 → step → 写回。投递和 Run 都只是在改这份记录，差别只在改什么——没有第二种事实来源。

**Status**: accepted；「step 是纯的、确定性的，所以……可以原样重放」这条**论据**已由 **ADR-0012** 修正（决定本身不变：单一事实来源、存盘点、Run 不等 effect 全部照旧）；「带版本写回」与「冲突语义」两节已由 **ADR-0013** 取代——写入是一次事务，内核不再认识版本号。

## 决定

- **单一事实来源**。没落盘的推进等于没发生。进程被驱逐、崩溃、换机器之后，唯一能读的就是快照。
- **身份**。工作流 id 由实例化方指定或框架生成；不透明字符串，等于 store key，内核不解析格式。碰撞报错，不提供"已存在就复用"的开关——幂等由调用方 `load` 后自己表达。
- **生命周期**。`active` / `halted` 两个状态。静止是从快照推导的（所有邮箱为空），不是状态位。没有"完成"；删除是 `drop`，记录整体消失，不留墓碑。
- **不记模板出处**。快照里没有 `origin`。工作流不知道自己来自哪份模板（ADR-0002）。
- **存盘点只有两处**：出图之前（effects 记进快照）、Run 结束（有改动才写）。纯图内的 `sends` 不单独落盘。
- **Run 不等 effect**。图内工作做完就返回，哪怕还有在飞 effect；结果回来是一次新的投递。所以**静止不等于"没有在飞的 effect"**——一个静止的工作流可能正等着模型回话。
- **投递 = 对目标节点邮箱做一次追加**。at-least-once，内核不去重；消息没有内核生成的 id。
- **并发控制归存储**（ADR-0013）。一次推进（读快照 → step → 写回）是存储的**一次事务**，`SnapshotStore.commit(id, change)` 提供它；内核没有版本号、没有冲突类型、没有重试循环。
- **转移日志是旁路**。独立 key、只追加、不进快照、不参与那次事务；它不是事实来源。
- **停住的表现**：投递被拒，`run` 空转返回。
- **恢复扫描归宿主，`Store` 只有 `load` / `create` / `commit` / `drop`**。内核只定义"什么叫需要恢复"并保证 `run` 幂等：`status === active` 且邮箱非空（该跑一次 Run），或有在飞 effect（该把同一个 `effectId` 重新交给执行器）。"谁去扫"是宿主的十行代码。

## 为什么

- **为什么不分步落盘**。step 的返回值可以原样重算（**论据已由 ADR-0012 修正**：可重放靠记录输出，不靠 step 确定），所以一整段图内推进崩溃后可以原样重放，外部一个字节都看不到。不可重放的是**出图**——effect 交给执行器、消息离开本工作流——所以必须在出图之前先让快照记住"我要做这件事"，含 `effectId`。
- **为什么 Run 不等 effect**。一次推进占着存储的写锁（ADR-0013），Run 若 `await` 一次三秒的模型调用，这份库里**所有**工作流都得等三秒——而且重试没有意义，它必须整段重放。让 Run 只包含纯 step，临界区就是毫秒级。这也是 `commit` 的回调必须是同步函数的直接原因。
- **为什么内核不去重**。去重键属于调用方（ADR-0001）。内核假装能去重，就得在快照里养一张无界的见过的表。

- **为什么没有 `Store.list()`**：若一个工作流落在一个 Durable Object 里，它只能列出自己的存储，永远列不出"全库哪些工作流有 pending"；写进 `Store` 就是定义一个只有一半实现能兑现的接口。Node 上恢复是"查 store 自己的索引"（ADR-0013 之后是 `SELECT id`），Workers 上是"调用方自己的索引 + 每个工作流的 alarm"，形状不同，假的统一接口只会让两边都以为自己实现了恢复。

## 代价（接受）

- 一条用户消息跨几次 effect 就是几次全量快照写（三节点 bot 示例约 6 次）。快照越大越贵。
- 跨投递方没有全序：同一会话要保序，只能由投递方自己按会话串行。
- 部署重叠期间同一条记录上的两次推进只会一先一后，不会互相作废——但先算的那次可能基于旧视图，见下一条。
- 崩溃会重发 effect：LLM 流整段重新生成。
- 每个宿主都要自己实现"谁需要跑"：Node 上约十行；Workers 上要自带索引（KV / D1）或依赖 alarm，等于把一部分可靠性外包给部署方。没有"全局待办视图"这个内核能力，运维要看积压只能看宿主自己的索引。

## 强烈推荐（不是契约）

宿主为每个工作流提供**串行入口**（并让恢复扫描能捡起"投递成功、Run 没跑"的悬挂态）（进程内 per-id 互斥；Workers 上是一个 DO 天然入口，库层再加锁）。存储的事务已经保证了**不丢更新**（ADR-0013）；串行入口只决定"两次推进谁先谁后"，从而决定中间态长什么样。

## Retired designs（不要重提）

- **投递队列 + 游标／队列即邮箱**：为了把投递从"改一份快照"降成 O(1)，赔上 FIFO 顺序和"静止可从快照推导"。投递变 O(1)，但真相源变两个，队列实现（如 Cloudflare Queues）还不保序。
- **Run 内 `await` effect**：见"为什么"第二条。
- **消息上的内核 id**：内核不去重，字段会撒谎。
- **快照里的 `origin`**：没有功能，只诱导人去"照模板同步"。
- **"完成"状态与墓碑**：静止 ≠ 结束，删除就是消失。
- **`Store.list()`**；**内核在启动时扫全库**（内核没有常驻进程）。
- **内核里的 `Revision` / `Conflict` / 重试**：ADR-0013 退役了它们。并发控制是存储的实现细节，不是内核的概念。

## 反转条件

- 如果每个宿主都在重复写同样的索引与游标，并且都写错过一次，就做成随框架发布的 app（`arbetslag serve`）或可选的 index 协作者接口——而不是把 `list()` 塞回 `Store`。
- 如果全量写成为瓶颈（快照接近平台单值上限 + 高频投递），"投递队列 + 游标"重新上桌。
- 如果某个目标平台做不到"出图前落盘先于出网"（Durable Objects 的 output gate 保证了这一点，自建宿主未必），存盘点要重排。
- 如果 effect 变成"必然长、且外部投递极其稀疏"，Run 内等待的代价会降到可忽略，可以重议。
