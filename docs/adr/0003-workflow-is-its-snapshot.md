# 工作流就是它那条快照，恢复归宿主

一份工作流在任一时刻就是 store 里的一条快照记录。内核没有跨 Run 的常驻内存态：推进 = 在存储的一次事务里载入快照 → step → 写回。投递和 Run 都只是在改这份记录，差别只在改什么——没有第二种事实来源。

**Status**: accepted

## 决定

- **单一事实来源**。没落盘的推进等于没发生。进程被驱逐、崩溃、换机器之后，唯一能读的就是快照。
- **身份**。工作流 id 由实例化方指定或框架生成；不透明字符串，等于 store key，内核不解析格式。碰撞报错，不提供"已存在就复用"的开关——幂等由调用方 `load` 后自己表达。
- **生命周期**。`active` / `halted` 两个状态。静止是从快照推导的（所有邮箱为空），不是状态位。没有"完成"；删除是 `drop`，记录整体消失，不留墓碑。
- **不记模板出处**。快照里没有 `origin`。工作流不知道自己来自哪份模板（ADR-0002）。
- ~~**存盘点只有两处**：出图之前（effects 记进快照）、Run 结束（有改动才写）。~~ **由 ADR-0016 修订**：落盘只在三个时刻（进来之前、交出不可重放的效果之前、闲下来之前）；Run 结束不再单独写。纯图内的 `sends` 仍不单独落盘。
- **Run 不等 effect**。图内工作做完就返回，哪怕还有在飞 effect；结果回来是一次新的投递。所以**静止不等于"没有在飞的 effect"**——一个静止的工作流可能正等着模型回话。
- **投递 = 对目标节点邮箱做一次追加**。at-least-once，内核不去重；消息没有内核生成的 id。
- **一次推进是 `SnapshotStore` 的一次 `commit`**（ADR-0013）。宿主给的 `SnapshotStore` 是激活的工作副本，真正的存储事务只在检查点发生（ADR-0016）。
- **转移日志是旁路**。独立 key、只追加、不进快照、不参与那次事务；它不是事实来源。
- **停住的表现**：投递被拒，`run` 空转返回。
- **恢复扫描归宿主，`Store` 只有 `load` / `create` / `commit` / `drop`**。内核只定义"什么叫需要恢复"并保证 `run` 幂等：`status === active` 且邮箱非空（该跑一次 Run），或有在飞 effect（该由激活重新交出去，ADR-0014）。"谁去扫"是宿主的事。

## 为什么

- **为什么不分步落盘**。一整段图内推进在崩溃后丢掉，外部一个字节都没看到：重跑一遍，结果可能不同（step 可以读时钟与随机，ADR-0004），但被丢掉的那一版从未被任何人观察到，所以两者都对。无法撤回的是**出图**——effect 交给执行器、消息离开本工作流——所以必须在出图之前先让快照记住"我要做这件事"，含 `effectId`。
- **为什么 Run 不等 effect**。一次推进占着存储的写锁（ADR-0013），Run 若 `await` 一次三秒的模型调用，同一份存储里的推进都得等三秒——而且重试没有意义，它必须整段重来。让 Run 只包含纯 step，临界区就是毫秒级。这也是 `commit` 的回调必须是同步函数的直接原因。
- **为什么内核不去重**。去重键属于调用方（ADR-0001）。内核假装能去重，就得在快照里养一张无界的见过的表。
- **为什么没有 `Store.list()`**：若一个工作流落在一个 Durable Object 里，它只能列出自己的存储，永远列不出"全库哪些工作流有 pending"；写进 `Store` 就是定义一个只有一半实现能兑现的接口。Node 上恢复是"查 store 自己的索引"（`SELECT id`），Workers 上是"每个工作流的 alarm + 宿主自己的索引"，形状不同，假的统一接口只会让两边都以为自己实现了恢复。

## 代价（接受）

- ~~一条用户消息跨几次 effect 就是几次全量快照写（三节点 bot 示例约 6 次）。~~ 由 ADR-0016 降到每轮 2 到 3 次检查点。
- 跨投递方没有全序：两个投递方同时投给同一份工作流，谁先进串行入口谁先。同一会话要保序，只能由投递方自己按会话串行。
- 换激活会重发 effect（ADR-0014）：LLM 流整段重新生成。
- 每个宿主都要自己实现"谁需要跑"：Node 上查自己的表；Workers 上靠 alarm 与自带的索引。没有"全局待办视图"这个内核能力，运维要看积压只能看宿主自己的索引。

## Retired designs（不要重提）

- **投递队列 + 游标／队列即邮箱**：为了把投递从"改一份快照"降成 O(1)，赔上 FIFO 顺序和"静止可从快照推导"。投递变 O(1)，但真相源变两个，队列实现（如 Cloudflare Queues）还不保序。
- **Run 内 `await` effect**：见"为什么"第二条。
- **消息上的内核 id**：内核不去重，字段会撒谎。
- **快照里的 `origin`**：没有功能，只诱导人去"照模板同步"。
- **"完成"状态与墓碑**：静止 ≠ 结束，删除就是消失。
- **`Store.list()`**；**内核在启动时扫全库**（内核没有常驻进程）。
- **内核里的版本号 / 冲突 / 重试**：并发控制是存储的事（ADR-0013）。

## 反转条件

- 如果每个宿主都在重复写同样的索引与游标，并且都写错过一次，就做成随框架发布的 app（`arbetslag serve`）或可选的 index 协作者接口——而不是把 `list()` 塞回 `Store`。
- 如果全量写成为瓶颈（快照接近平台单值上限 + 高频投递），"投递队列 + 游标"重新上桌。
- 如果某个目标平台做不到"出图前落盘先于出网"（Durable Objects 的 output gate 保证了这一点，自建宿主未必），存盘点要重排。
- 如果 effect 变成"必然长、且外部投递极其稀疏"，Run 内等待的代价会降到可忽略，可以重议。
