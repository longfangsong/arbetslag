# 节点定义是纯行为，节点不持有资源

节点定义只是一份数据和一纯 step：名字、版本、状态与 config 的 schema、可选的迁移。没有实例、没有构造、没有生命周期钩子；需要外部世界的一切——端口、连接、模型调用、外发——都不长在节点上，要么归宿主，要么走一次 effect。

**Status**: accepted

## 决定

- **节点定义是 interface，不是 class**。内核只见六样：`name` / `version` / `state` schema / `config` schema / `step` / 可选 `migrate`。能力清单封闭，没有 `init`、`start`、`onRetire`、`dispose`、`describe`。
- **config 有 schema**，在实例化与新增节点时校验。写错模板在落盘之前就被拒，不等到第一条消息进来。
- **`state` 在每次转移之后（落盘之前）与每次载入时各校验一次**。过不了就是"内核无法继续" → 隔离；坏状态绝不进快照。
- **版本是可比较的标签，内核只比较、从不解释**。快照里每条节点记录带着 `(name, version)`；注册表里每个名字只有一份定义——**当前部署的那一版**。
- **`migrate(state, fromVersion) → state`**：一次跳到当前版本，内核只调一次，输出由 `state` schema 校验。它是总函数，不返回 `Result`。**迁移只向前**：记录版本比在场定义新（回滚部署）→ 隔离，不让旧代码去猜新数据。
- **"纯"指不产生副作用、不持有资源**，不承诺确定性：`step` 可以读时钟与随机数。冲突重试会让同一条消息被处理两次，两次结果可能不同，以落盘那次为准。
- **内核没有 kind**。形状里只有节点定义的名字。入口、出口、工具、supervisor 都是位置与行为的描述，不是种类；"每个节点都能收消息"让按种类分发的接线表失去存在理由。
- **没有复合节点**。一份工作流是一张扁平图，节点原子；组合只在模板层（实例化前展开）与运行时新增节点（长出平级节点）。
- **监听、连接、外发一律不在节点里**。监听器归宿主，一次性的外部动作是 effect。

## 为什么

四条硬事实，任何一条都足以否掉"节点持有资源"：

- **载入必须是纯读**。冲突处理是"丢弃内存推进、重载重跑 ≤3 次"，恢复扫描可以在任意时刻载入同一份快照。节点若有 `start()`，载入就变成绑端口、开长轮询、建连接。
- **部署重叠是常态**。两个进程同时持有同一份工作流，就是两个监听器、端口冲突或重复消费。
- **一图一进程不成立**。一个进程只有一个端口，却承载多份工作流；Workers 上根本没有 socket，请求由平台路由。
- **不可序列化的资源不能由快照里的位置拥有**。节点的一切都要能从快照重建；socket 和 client 不能。

另外几条：

- **config schema 是同一条思路的另一侧**：模板是人手写的，写错应该在实例化时被拒绝，而不是让某个节点在第一条消息到达时抛异常、乃至隔离整份工作流。
- **注册表只放最新一版**：放多版本等于让内核在部署重叠期替应用决定"该用哪一版"。应用知道自己部署了什么，内核不知道。
- **状态每步校验**：坏状态一旦写进快照，之后每次载入都会炸，而且事实已经被污染；每次推进本来就要全量序列化，一次 schema 校验不算额外负担。
- **允许时钟与随机**：模型里没有"重放转移"（只有 at-least-once 投递），确定性换不到任何东西；effect 的结果本来就由外部世界决定，内核注入一个时钟只是在假装确定。要确定的时间，就把它放进消息里。
- **不要 `describe()`**：自由文本是第二份真相，而它能说的（名字、config、状态、出口）都已经有结构可读。没有消费者时定下的形状，等到有消费者时一定是错的。

## 代价（接受）

- class 写法出局：没有构造参数、没有闭包捕获 client。
- 按 kind 分发的代码出局（旧的 `Project.sink()` 那一类）。
- 问"这个节点是不是出口/工具"没有答案，只能看它在图上的位置和它出什么 effect。
- 动态长出来的图没有折叠，会摊成一大片平级节点。
- **回滚部署会让在跑的工作流隔离**：恢复要靠重新部署新版本，或者丢弃它们。
- **节点定义没有自由文本自述**：要给人看的说明只能从六个字段派生。

## Retired designs（不要重提）

- **运行时 `Actor` 对象**（信箱 + 异步 consume 循环）：节点没有实例。
- **`node kind` 枚举与按 kind 投递**。
- **节点类的 `init` / `start` / `onRetire` / `dispose` 钩子**。
- **入口节点自己持有 HTTP server 或长轮询**（`InputAdapter` + `WebhookServer`）：监听器归宿主，入口节点只是收到外部投递的普通节点。
- **复合节点**（节点内部是一张子图）。
- **`describe()` 自由文本自述**：没有消费者，是第二份真相。
- **注册表里多版本并存、按 `(name, version)` 查表**：只认最新一版，版本落后靠 `migrate`。
- **链式迁移表**（`migrations: {1: fn, 2: fn}`）：要求每对相邻版本的迁移函数都还在场，回滚即缺环。
- **注入时钟/随机的"确定性 step"**：内核本来就无法让 effect 的结果确定。

## 反转条件

- 如果部署形态变成"一份工作流一个容器"（一图一进程，天然独占端口），"节点持有监听器"重新有讨论余地。
- 如果平台能保证"一份快照对内核而言恰好载入一次"，钩子的代价会下降；只要恢复扫描还在，就做不到。
- 如果出现"同一进程必须同时服务多个部署版本"的形态（长跑的多租户宿主），注册表就要放宽到多版本。
