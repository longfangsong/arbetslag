# 边界只有触发器，内核只有一个动词

内核只提供 `run(workflow)`。向一份工作流投一条消息，就是一次带版本校验的写（消息进目标节点的邮箱）加一次 `run`。图外的一切——webhook、轮询、cron、命令行、另一个工作流——都是触发器，是 store 与 `run` 的客户端。

**Status**: accepted

## 为什么

- 投递和图内节点的 `sends` 是同一个操作：消息进目标节点的邮箱。外部来的消息唯一的区别是没有发件人。为此单设一个 `dispatch` 动词，等于让内核假装知道"外部存在"。
- 入口不是节点。按节点自己的定义（有邮箱、有私有状态、只在收到消息时推进），入口三条都不满足。所以模型里没有"入口节点"，也就没有它的输入信封 `Event`。
- 图内因此只有一种信封：**消息**。

## 代价（接受）

- 一个 bot 一个轮询、webhook 去重、游标、按会话切分——全是调用方的责任，框架不保证。
- 模板里可以有触发器声明段，但**内核不读它**：同一份模板有两个读者，内核只认图。

## Retired designs（不要重提）

- **入口节点 + `Event` 信封**：入口不满足节点的定义。
- **内核持有的路由表 `key → workflowId`**：它是调用方的一张表。
- **模板里的 `channels:` 绑定 + `per:` 切分**：切分粒度由实例化方决定，模板不表态。
- **`dispatch` 作为内核动词**：投递是写，不是语义。
- **`forward` 结构字段**：跨工作流不是结构操作，见 ADR-0002。

## 反转条件

如果每个调用方都在重复实现同样的路由、去重、游标，那说明该把它做成一个随框架发布的 app（`arbetslag serve`），而不是把入口搬回内核。
