# 一个信封，三个字段

图内只有一种信封：谁发的、哪一类、载荷。目标不在信封上（路由是投递的事），没有内核 id，也没有第二个塞数据的地方。而"哪一类"就是**发送方那个出口的名字**——一条路只有一个名字，接线用它，接收方分派也用它。

**Status**: accepted

## 决定

- **信封三字段**：`from`（谁发的；图外投递与效果回执没有）、`type`（哪一类）、`body`（载荷，JSON）。**目标不在信封上**。
- **没有内核 id**：应答配对靠 `from`；应用自己的关联 id（`callId`、会话 id）放 `body`。
- **端口名就是消息的类别**：一条发射口只有一个名字，它既是形状里接线的依据，也是接收方 `switch (msg.type)` 的依据。端口声明里带 body schema，发送时按它校验。
- **一条发送必须有一个端口**（目标可选：显式给出目标 id 时不经过边，用于发给运行时才有的节点、或回复 `from`；端口仍然给出消息的类别并校验 body）；不存在"只有目标没有类别"的发送。
- **入站形状归应用**：节点定义不声明自己接受什么——没有接收侧端口，也没有 `accepts` 表。同一份消息 schema 由发送方与接收方在应用侧共享；节点在 step 里自己收窄载荷。内核只保证结构：类别是非空字符串、载荷是 JSON。
- **`@` 前缀保留给内核**。节点发出的消息里出现 `@` 开头的端口名 = bug = **停住**（不是丢弃）。
- **图外投递的类别是触发器的输出名**（ADR-0001）：触发器种类声明输出及其 body schema，从触发器出发的边接到节点；节点分派用的就是这个名字。
- **内核信封是普通消息**：`@effect.end`、`@await.broken` 走同一条邮箱、同一条通道，只是类别由内核写。

## 为什么

- **目标为什么不在信封上**：信封若带目的地，路由就有两处——信封里的和形状里的——而形状校验只看得到后者。一次投递只能有一个决定者。
- **为什么端口名即类别**：两个名字意味着"这条边传的是什么"有两个答案，而形状校验只看得到端口名；允许分叉的结果是分派逻辑与接线各自漂移。
- **为什么入站形状归应用**：内核无法判定"发送方端口的 schema"与"接收方接受的 schema"一致（zod 的等价性不可判定），能做到的只有运行时炸；把唯一一份 schema 放在应用侧，两端的类型都从它推，真相只有一处。
- **为什么保留 `@`**：`@effect.end` 靠类别认，前缀不设界，任何节点都能伪造"你的效果完成了"。信任边界不值得为一个前缀省钱。

## 代价（接受）

- **中介节点不能原样转发**：fork / relay 只能用自己的端口发，下游看到的类别变成它的端口名；要保留原类别就包进载荷。转发节点本来就应该显式知道自己转的是什么。
- 每个节点定义里要写载荷的收窄样板（可以用一个 helper 收掉）。
- **图外投递的 body 由触发器种类的输出 schema 校验，但接收侧仍不声明**：和图内一样，发送方与接收方的一致性靠应用约定（见"入站形状归应用"）。

## Retired designs（不要重提）

- 信封上的目的地字段。
- 消息上的内核 id。
- 信封上的 `correlation`（关联标签只见于效果请求，由回执带回）。
- 分离的"端口"与"类别"两个字段。
- 接收侧的 `accepts` 表 / 接收侧端口。
- 应用可用的 `@` 前缀。

## 反转条件

- 如果共享 schema 在实践中退化成"每个节点抄一份"，说明应用侧缺一个约定；届时可以讨论内核**可选**接受一个 schema 提示（仅用于开发期校验，不进模型）。
- 如果出现必须原样转发的通用中间件（代理、审计、录制回放），类别与端口名会重新分离。
