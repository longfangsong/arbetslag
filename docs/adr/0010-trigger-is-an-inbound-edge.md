# 触发器是形状里的一条入边

触发器是工作流自己持有的一份声明："用 kind K、配置 C，把外部事件以类别 T 投给我的节点 N"。它是形状的第三类成员（节点、边、触发器），随快照持久，任何节点都能在转移里增删它。宿主只提供各个 kind 的实现，并按工作流当前声明的内容去建、改、拆真正的监听。内核存声明、校验声明，但从不执行触发器。

**Status**: accepted（ADR-0001 中关于触发器的表述已据此改写）

## 决定

- **触发器 = 形状里一条从图外指向节点的入边**：`{ id, kind, config, to, type }`。与边同构：边是"从某个节点的出口通向另一个节点"，触发器是"从图外的某个事件源通向某个节点"，只是起点不是节点。
- **它不是节点**：没有邮箱、没有私有状态、不会被推进。术语表里"触发器不是节点"不变。
- **来源是快照，不是模板**：模板里的 `triggers:` 段只是实例化时的初始值，与节点一样读一次，之后工作流与模板无关（ADR-0004）。宿主需要哪些监听，只问快照。
- **图可以改它**：增删触发器与 spawn / connect / retire 同类，共用同一套"先全量校验、再应用"的改图流程（ADR-0002）。
- **回收节点连带删除指向它的触发器**，与删边同一条规则。
- **`type` 是触发器投出的消息类别**，与边的端口名同构（ADR-0009）：节点按它分派；没有它节点无从分辨。
- **内核认识 kind 的名字与 config schema，不认识它的行为。** 宿主把触发器 kind 的定义（名字 + config schema）注入给内核，与节点定义同属一张注册表。内核不启动、不执行任何触发器。
- **声明不合法 → 隔离**：未知 kind、config 不符合该 kind 的 schema、`to` 指向不存在的节点，在实例化、改图转移、载入时一律按"改图非法"处理，隔离整份工作流。宁可停住，也不静默丢掉入口。
- **声明合法但起不来 → 不隔离**：端口被占、token 被拒、网络不通是外界的暂时状况。宿主把这条触发器记为未就绪，重试并报告，工作流本身继续运行。
- **对账归宿主，内核不推送**：宿主每次 `run` 落盘之后，把快照里的触发器声明与当前在跑的监听对比，多了就起、少了就停、变了就重建。内核只保证"快照里的声明是事实来源"（与 ADR-0006 同一立场）。
- **图外投递仍然没有 `from`，也不经过边。**
- **没有"切分"这个概念**：触发器属于某一份工作流，事件天然只投给它。"一个 chat 一份工作流"这样的映射由一份持有触发器的"总机"工作流在节点里实现：收到消息后发一条跨工作流投递的 effect，宿主的执行器负责载入、必要时实例化、投递、`run`。内核不提供 get-or-create。

## 为什么

- **为什么不是宿主级**：触发器的出现、消失、改配置本来就是工作流行为的一部分（例如某个节点决定"从现在起监听这个源"）。若它活在宿主配置里，图无法改它，快照也无法说明"这份工作流现在对外开着哪些入口"。
- **为什么是入边而不是一种新东西**：它与边在生命周期、连带回收、改图校验上完全重合，复用同一套规则，术语表只多一个词，不多一套机制。
- **为什么内核要认 schema 却不认行为**：校验 config 是纯检查，不碰外界，与节点定义的 state schema 同类；执行则必须留在宿主，因为不同部署（Node / Workers）的监听方式根本不同（ADR-0006 的教训：不要用统一接口掩盖平台分叉）。
- **为什么起不来不隔离**：隔离是"内核拒绝再推进"。端口冲突是外界状况，隔离会把它放大成整份工作流停摆，而且隔离是人工解除的，暂时故障不该要人。

## 代价（接受）

- 每个宿主都要实现对账：读快照、diff、起停监听。这是 ADR-0001 里"调用方责任"的一部分，只是现在有了明确的事实来源。
- 触发器 kind 的注册表是宿主与内核之间的又一份契约；kind 的 schema 改动同样会遇到迁移问题（本 ADR 不定，留待概念 8 之后）。
- 总机工作流是一份特殊的常驻约定：它持有 bot 级的触发器，必须先于任何 chat 工作流存在，由应用在引导时创建。

## Retired designs（不要重提）

- **宿主级触发器 / 宿主启动时读模板的 `triggers:`**：来源是快照，不是模板文件。
- **模板声明触发器名字、宿主另配绑定**：模板应自包含（但只提供初始值）。
- **触发器声明里的 `workflow: { id: ... }` 切分规则**与"切分"概念本身。
- **内核对触发器 kind 一无所知**：它至少要认名字与 config schema，否则无法在载入时隔离非法声明。
- **宿主可写入的隔离状态**：隔离仍然只表示内核拒绝推进。

## 反转条件

- 如果每个宿主的对账代码高度重复，就把它做成随框架发布的一个库（不是内核职责）。
- 如果"声明合法但起不来"在实践中常需要人为介入，重新讨论是否引入"未就绪"的持久标记。
