# 触发器是订阅：监听器归部署，路由归宿主

一个外部事件源（一个 bot token、一条 webhook 路径）只能有一个监听：Telegram 同一个 token 只允许一路 `getUpdates` 或一个 webhook。可是触发器写在每份工作流自己的形状里，于是"一个会话一份工作流"只能靠一份持有全部触发器的总机，在热路径上把每个事件转发一遍。这里把这两件事拆开：**监听器**是部署里的资源，一个事件源一个；**触发器**是工作流对某个监听器上的一部分事件的**订阅**，仍然写在形状里、由图自己增删。事件从监听器到工作流之间，由宿主的**路由**按订阅投递。

**Status**: accepted

## 决定

### 监听器

- **监听器 (Listener)** = 部署配置里的一项 `{ id, kind, config }`。它持有密钥（token、签名密钥），一个外部事件源恰好一个。它不在任何快照里，图改不了它。
- 监听器的实现与触发器种类同名（Node 上 `telegram` 是长轮询，Workers 上是一条 webhook 路由）。它把每个外部事件变成 `{ output, body, eventId? }` 交给路由：
  - `output`、`body` 与触发器种类的 `outputs` 声明对应；
  - `eventId` 是来源自带的事件 id（Telegram 的 `update_id`），没有就不给。
- 监听器起不来（token 被拒、端口被占）是部署级的**未就绪**：报告、重试，不涉及任何工作流。
- 路由把事件**写进发件箱之后**，监听器才向来源确认（回 200、推进 offset）。

### 触发器 = 订阅

- 触发器声明扩展为 `{ id, kind, listener, match?, group?, priority?, config }`。形状里的位置、输出即端口、从它出发的边，全部不变（ADR-0001）。
- **匹配函数 (Matcher)** 是订阅唯一的筛选手段。它是注册表里与节点定义、效果种类、触发器种类并列的第四种东西：`{ name, config schema, match(output, body, config) → boolean }`，要求同步、纯、便宜。
  - 订阅的 `match` 写成 `{ fn, config }`，省略即 `always`。
  - 框架预置 `always`、`chatIs`、`textMatches`、`fromUser`，以及组合用的 `all` / `any`；应用可以注册自己的。
  - 快照里只存名字与 config，**从不存代码**。
- **分组 `group`**：字符串，默认 `""`。一个分组是一个独立的分发域：同一个事件在**每个**分组里各分发一次，分组之间互不影响。
- **优先级 `priority`**：整数，默认 0，只在同一分组内比较。在每个分组里，事件投给**命中的订阅里优先级最高的那一层**中的**全部**订阅；该分组更低的层收不到。同一层内无序、全收（与 ADR-0011 的边同一语义）。同一份工作流里多条订阅都在那一层命中，就各投各的（它们是不同的触发器、不同的边）。
- **兜底不是一个概念**：它就是同一分组里一条优先级更低的 `always` 订阅。只有该分组更高的层没人命中时，它才收到。
- **观察者也不是一个概念**：审计、统计这类"每条都要看、但不算处理"的订阅放进自己的分组（例如 `group: "audit"` + `always`），它挡不住任何别的分组。
- 内核的校验沿用 ADR-0001：未知种类、config 不合 schema、`match.fn` 未注册或其 config 不合 schema、`group` 不是字符串、`priority` 不是整数 → 实例化时抛错、改图时整批被拒、载入时停住。`listener` 引用部署里不存在的监听器**不是**声明非法（部署可以晚到），而是宿主侧的未就绪。

### 路由

- **路由索引**：订阅的投影 `listener → [(workflowId, triggerId, match, group, priority)]`。宿主在每份工作流提交之后**对账**：把快照里的触发器声明与索引里这份工作流的行对比，多删少补（ADR-0001 的对账，对象从"监听"换成了"索引行"）。对账失败（写索引出错）→ 那条订阅**未就绪**，宿主重试并报告。索引不是事实来源：丢了可以从全部快照重建。
- **路由**：对每个事件，取出该监听器上的**全部**订阅，按分组分开；每个分组内按优先级从高到低逐层执行匹配函数，遇到第一个有命中的层就停 → 把各分组选出的那一层的命中者合在一起，在**一次原子写**里为每个目标插一行**路由发件箱** `(target, trigger, output, body, listener, eventId, seq)` → 监听器确认来源 → 通知各目标的激活。
  - 匹配函数抛错或未注册：按不匹配处理，并报告。
  - 只有声明了这个输出（`outputs(config)` 里有它）的订阅才是候选；body 不符合某条订阅的输出 schema，那条订阅不是候选，并报告。
  - 没有任何分组有命中：丢弃，并在宿主日志里记一条。
- **去重在发件箱上**：`(target, listener, eventId)` 唯一，重复插入忽略。来源在确认之前重投（路由写完发件箱、确认之前崩溃），不会产生第二行。发件箱的行按保留期（默认 24 小时，大于来源的重投窗口）清除，不按消费清除，所以去重窗口就是保留期。没有 `eventId` 的事件不去重。
- **游标**：每个目标工作流有一个发件箱游标。激活被通知（或恢复扫描）时，在串行入口里读取 `seq > 游标` 的行，在**同一次存储事务**里把它们按 `seq` 依次投进邮箱（等同于每行一次 `deliverFromTrigger`）并推进游标。游标是宿主的表，与快照同库同事务，不进内核的快照。于是从发件箱到邮箱是 exactly-once，不需要额外的去重表。
- **停住期间**：激活不消费发件箱，行留在原地；`resume` 之后按 `seq` 依次投进去。超过保留期仍未消费的行被丢弃并报告。
- **通知丢了不要紧**：恢复扫描会捡起"发件箱里有比游标新的行"的目标（Workers 上是定时扫一遍 D1，Node 上是启动时扫一遍）。

### 存储位置

| | Node | Workers |
|---|---|---|
| 快照、发件箱游标 | 同一个 SQLite 文件 | 那份工作流的 DO 自己的 SQLite（同一事务） |
| 路由索引、路由发件箱、工作流索引 | 同一个 SQLite 文件 | D1 |

两边表结构相同，宿主只在"怎么开事务、怎么通知、怎么唤醒"三处分叉。Node 也走发件箱 + 游标，不走"同一个文件里直接写邮箱"的捷径：本地要复现线上的投递语义。

### 总机与新会话

- **总机**是一份持有低优先级 `always` 订阅（默认分组、`priority: -1`）的普通工作流，由应用在引导时创建。会话工作流的订阅在默认分组的 0 层，所以已有会话的事件不经过总机；只有新会话的第一条事件（默认分组 0 层没人命中）落到总机。别的分组里的订阅（审计等）不影响这一点。
- **`workflow.spawn`**：框架提供的效果种类（声明随内核发布，与 `graph.mutate` 一样；执行归宿主，因为它跨工作流）。
  - `input = { id, template, params?, forward? }`：按名字从部署的模板目录取 `template`，用 `params` 填它的参数（总机按会话把 chat id 填进去，匹配函数的 config 引用它），实例化 id 为 `id` 的工作流（ADR-0018）；`forward = { trigger, output, body, eventId? }` 是要转交给它的那条事件。
  - `id` 已存在不是失败：跳过实例化，只转交。`result` 为 `{ ok: true, created }` 或 `{ ok: false, error }`。
  - 执行顺序固定：先实例化，再在**一次原子写**里写入 `forward` 那一行发件箱与新工作流的全部索引行。之后到达的同一会话的事件直接命中新工作流的订阅，其 `seq` 一定大于被转交的那一行。
  - 转交不会造成重复：一条事件只有在默认分组 0 层没人命中时才落到总机，也就是说那一刻会话工作流没有收到它。

## 为什么

- **为什么拆开监听器与订阅**：资源的个数由外部决定（一个 token 一个），订阅的个数由工作流决定（一个会话一份）。两者绑在一起，要么每份工作流各开一个监听（外部不允许），要么一份工作流持有全部监听（总机上热路径）。ADR-0001 要的"工作流自己决定响应什么外部事件"由订阅兑现；监听器只是一根管子，图本来就不该关心管子有几根。
- **为什么只有匹配函数，没有声明式的键**：键与匹配函数会成为同一个条件的两处表达（"只要 chat 42"写在键里还是写在函数里），两处还可能互相矛盾——这正是 ADR-0011 拒绝第二处声明的理由。订阅只说"什么事件算我的"，用一个函数说完。
- **为什么路由逐个跑**：最简单、语义一眼可见。代价是每个事件 O(该监听器上的订阅数)，规模小时无感；索引是将来的优化，而它可以做在匹配函数的定义上、不进快照（见反转条件），所以现在不做不会留下迁移负担。
- **为什么要优先级**：兜底本身就隐含顺序——"别人都不要，才轮到我"。没有顺序，一条 `always` 订阅收到的是**全部**事件，总机就回到了热路径上。顺序不能来自声明位置：订阅分散在不同工作流的形状里，跨工作流没有统一的排序处，而形状是集合（ADR-0002、ADR-0012）。所以它只能是订阅上一个显式的数字。
- **为什么是"最高命中层全收"，而不是"第一个命中者独得"**：一个事件要能投给多份工作流。层内全收保留了这一点，层间的先后给出了兜底。
- **为什么要分组**：只有一个全局的分层，"互不影响、各拿一份"和"同一个域内的先后与兜底"就被压进同一个数字里，一条高层的全收订阅（审计）会挡住所有低层（包括总机）。成熟的分发系统都把这两件事拆成两个维度：python-telegram-bot 的 handler group（各组独立处理同一个 update，组内才有先后）、RabbitMQ 的 alternate exchange（兜底只对一个 exchange 定义）、EIP 的 Wire Tap（观察者不参与路由判断）。分组就是第一个维度，优先级是第二个。"观察者"因此不需要单独的标记：它只是独占一个分组。
- **为什么层内全收，而不像 python-telegram-bot 那样组内独得**：组内独得要求组内有先后，而订阅分散在不同工作流里，没有统一的先后（同上一条"为什么要优先级"）。
- **为什么匹配函数要注册，不能存代码**：Workers 禁止 `eval` / `new Function`，快照里的代码字符串根本跑不了。而且快照只存名字与 config、行为在部署里，正是 ADR-0004 的主线。
- **为什么要发件箱，而不是路由直接把事件投进每个工作流**：Workers 上 N 个目标是 N 个 DO、N 次独立的写，不可能原子。投到一半失败，来源重投，前几个目标就收到两次。D1 的一次 batch 可以原子地写 N 行，之后每个 DO 各自 exactly-once 地拉取。
- **为什么去重做在发件箱，而不是内核**：ADR-0003 不让内核养一张"见过的 id"表，那张表无界，而且放在快照里。发件箱的去重是有界的（保留期），在宿主的表里，并且对所有工作流只做一次。
- **为什么停住时行留在发件箱**：路由已经向来源确认了，此时再拒绝就等于丢消息。留在发件箱，`resume` 之后什么都没丢。
- **为什么 `workflow.spawn` 带 `forward`，而不是"先建、再让路由重投"**：总机收到的那条事件已经被路由处理并确认过了，没有第二次路由。把转交和索引写在同一次原子写里，是保证"后到的事件不会越过第一条"的唯一方法。
- **为什么这不是 ADR-0011 拒绝的 topic / 总线**：ADR-0011 拒绝的是**形状内部**的 topic，理由之一正是"名字一旦全局，天然想跨工作流"。这里要的恰恰就是跨工作流，而它发生在宿主层，不在任何一张形状里：形状里仍然只有触发器和边。

## 代价（接受）

- **路由成本随订阅数线性增长**：每个事件都要取出该监听器上的全部订阅、逐个跑匹配函数。一个会话一份工作流时，订阅数约等于会话数，而事件数也随会话数增长，所以总成本约为会话数的平方。Workers 上每个事件要从 D1 读出全部订阅行。
- **同一分组内，高层的全收订阅仍会挡住低层**：这是分层的本意（兜底就靠它），但把审计误放进默认分组，总机就收不到了。
- **分组名与优先级都是跨工作流的约定**：`""` 是会话域、`"audit"` 是审计、0 是会话、-1 是兜底，这些含义由应用自己约定，框架只比较。分组名写错一个字，订阅就悄悄落进另一个分发域；路由不会报错。
- **投递多了一跳**：监听器 → 发件箱 → 通知 → 激活拉取。比直接写邮箱慢一次存储往返。
- **索引是投影，会滞后**：工作流刚加的订阅在对账完成前不生效，这期间的事件按旧索引路由（可能落到总机）。对账失败的订阅一直未就绪，直到重试成功。
- **会话开头的乱序窗口**：新工作流的索引生效之前，同一会话的多条事件都会落到总机；总机交出的多个 `workflow.spawn` 之间没有顺序保证（ADR-0006），被转交的顺序可能与到达顺序不同。要保序，总机在自己的状态里按会话串行交出（等上一个回执再交下一个）。
- **匹配函数的部署耦合**：删掉一个还被订阅引用的匹配函数，那些订阅在路由时一律不匹配（报告，不停住）；载入时那份工作流停住（声明非法）。
- **停住的工作流会在发件箱里攒行**，超过保留期的行被丢弃。
- **新增一个注册表种类**（匹配函数）、一个框架效果（`workflow.spawn`）、三张宿主表（路由索引、路由发件箱、游标），以及一份部署配置（监听器）。

## Retired designs（不要重提）

- **触发器 = 一份由宿主为每份工作流起停的监听**：外部事件源不允许多个监听。
- **总机在热路径上**：每个事件都先经过一份工作流，在那里写一次、在那里串行、它停住则全体停住。
- **订阅声明里的键 / 键前缀**：与匹配函数是同一条件的第二处表达。
- **订阅的认领模式**（`claim` / `observe` / `fallback`）、**"收到但不阻挡下层"的标记**：兜底由同组内的优先级表达，观察者由独立的分组表达，都不是一种身份。
- **一个全局的分层**（没有分组）：高层的全收订阅会挡住所有人。
- **按声明位置排序的订阅**，以及**第一个命中者独得**。
- **存进快照的匹配代码**（字符串、AST、`eval`）。
- **路由直接逐个写入目标工作流**（没有发件箱）。
- **内核里的去重表**，以及**按消费删除发件箱的行**（会把去重窗口缩成零）。
- **停住时拒绝触发器的投递、让来源重投**。
- **"同一个文件就直接写邮箱"的 Node 捷径**。
- **`workflow.spawn` 只建不转交、由路由重投第一条事件**。

## 反转条件

- 如果逐个跑的路由成本成为问题：给**匹配函数的定义**加一个可选的 `index(config) → { field, value }`，契约是"`match` 为真 ⇒ `body[field] === value`"（必要条件）；路由先按索引取候选、再跑 `match`，没有 `index` 的订阅仍然逐个跑。它只在部署代码里，不进快照，已有工作流不用迁移。**不要**把键加回订阅声明。
- 如果分组名写错成为真实痛点：让部署声明合法的分组名清单，宿主在对账时把不在清单里的分组记为未就绪（不进内核，不停住）。
- 如果会话开头的乱序在实践中频繁出现，在路由层引入"按会话的待认领队列"，而不是让每个总机各写一遍串行。
- 如果多一跳的延迟成为问题，可以在单目标且同一激活的情况下走快路径，但发件箱的写不能省：它是确认来源的前提。

## 验收

1. **分组与分层**：默认分组里，一个事件命中 0 层的 2 条订阅和 -1 层的 1 条 → 0 层两条各收到一次，-1 层没收到；0 层无人命中 → -1 层收到。另有 `"audit"` 分组的一条 `always` → 两种情况下它都收到，且不影响默认分组的结果。
2. **路由崩溃后来源重投**：发件箱写完、确认前崩溃，来源用同一个 `eventId` 重投 → 每个目标仍只有一行。
3. **激活崩溃**：提交了投递、清理之前崩溃 → 重启后不重复投递（游标）。
4. **停住**：停住期间到达的事件留在发件箱；`resume` 之后按 `seq` 依次进邮箱。
5. **总机**：两个不同 chat 的第一条消息 → 两份新工作流；同一 chat 的第二条消息不经过总机（看总机的转移日志），并且排在第一条之后。
6. **匹配函数**：改图时引用未注册的匹配函数 → 回执失败；路由时匹配函数抛错 → 不匹配并报告，其它目标照常。
7. **Node 零配置**：全部表在同一个 SQLite 文件里，`node main.ts` 不需要任何外部服务。
