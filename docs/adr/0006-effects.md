# 效果：种类要注册，回执是一次投递，"出口"不是概念

节点在一条转移里交出去一次外部动作请求（效果）。内核不执行它，只把它记进快照、交给注入的执行器；做完之后，结果作为一条消息回到发起它的那个节点。没有回调，没有 await，也没有第二条通道。

**Status**: accepted

## 决定

- **效果是数据**：`{ kind, input, correlationId? }`，全可序列化。**kind 由宿主注册**：名字、`input` schema、回执结果（`result`）schema，与节点定义、触发器种类同属注入给内核的注册表（ADR-0004、ADR-0001）。内核在 step 返回时校验 `effects`：未知 kind、`input` 不合规 → **停住**（ADR-0008）；内核仍不执行任何效果。执行器现场把它解释成 HTTP、模型调用、文件写入；节点只交意图——何时落盘、是否已发出、发了几次，全由内核决定。
- **回执回到发起它的节点，这在发起那一刻就定死**（在飞记录里的 `origin`）。不看边、不看端口、不看 `type`；节点也不能事后改变主意把回执转给别人。
- **`graph.mutate` 是框架提供的效果种类**（ADR-0002）：`input` 是一批改图操作，`result` 是成功或违规列表。内核给一个纯函数 `applyGraphMutation(registry, snapshot, ops)`（先全量校验，再按固定顺序应用），由执行器调用；执行器载入快照、调用它，并在**同一次写**（一次存储事务，ADR-0013）里应用改动、删在飞记录、给 origin 追加回执。内核仍不执行任何效果——执行的是执行器，只是这个种类的执行逻辑由框架随内核发布，不由宿主按平台各写一份。
- **回执不需要边**：`@effect.end` 没有 `from`——"回给谁"在记录里，不在消息上。origin 已被回收 → 结果与记录一并丢弃。
- **信封只有一条：`@effect.end`**。它的 `body` 由内核包一层：`{ correlationId?, result }`，`correlationId` 是请求时给的那个，`result` 才是种类声明的形状；成功与失败是 `result` 的两种形状，不是两个信封。没有这一层，`correlationId` 无处带回（种类声明的 schema 里不会有它）。
- **没有 chunk**。图不承载增量：界面要流式，由宿主在执行器侧旁路推（SSE / WebSocket），不经邮箱。
- **在飞记录进快照，回来即删**。不留历史；诊断靠转移日志（旁路、可截断）。
- **追加邮箱与删记录是同一次写**：那条记录是一次性令牌。于是**对图 exactly-once，对外部世界 at-least-once**——外部动作可能做两次，图只会看到一次结果。
- **`correlationId` 是字符串，由作者给，内核原样带回**。`effectId` 是内核的幂等键，step 看不见；节点靠自己的 `correlationId` 把回执和当初的请求对上。
- **Run 不等效果**。静止与在飞效果无关：静止是"没有可执行的转移"。
- **没有"出口节点"这个概念**：出口只是 step 里会交出某类效果的普通节点，内核眼里与别的节点没有区别，不进术语表。出口型效果的回执照样一定有，`result` 可为空。
- **未识别的消息类别由 step 显式处理**：内核不提供"默认丢弃"。写一个 `default: return { state }` 就是显式忽略，同样适用于出口节点接住的空 `@effect.end`。
- **用效果的节点必须认识 `@effect.end`**，内核不检查（接收侧没有入站声明，也就无从检查）。漏接的表现是**静止**，不是停住。

## 为什么

- **为什么不做第二条通道**：图内只有邮箱一条通道，"一次投递 = 一次追加 + 一次 run"才是唯一的写路径。任何"结果直接回到某个活着的函数"的做法，都要在快照之外维护等待者，而载入必须是纯读、部署重叠是常态（ADR-0004 的四条硬事实）。
- **为什么用 origin 而不是 `from`**：回执的发件人是内核；把 origin 放进消息，等于给内核开一个可被伪造的字段。放记录里，节点无从伪造。
- **为什么只有一个 `@effect.end`**：失败是正常结果，不是内核故障。做成第二个信封，就要每个节点写两次分派，"效果的终点"也会有两套生命周期。
- **为什么去掉 chunk**：chunk 要"易失、不落盘"，就必须绕过邮箱——那它就是一条秘密通道，而它存在的唯一理由是给人看。观察面不该长在内核的写路径上。
- **为什么不检查回执有没有被接住**：接收侧没有入站声明（消息形状是应用的事），内核也没有观测"step 消费了什么"的手段；强行检查只能造出一个假钩子。

- **为什么 kind 要注册**：校验 `input` 是纯检查、不碰外界；让非法效果在交出那一刻就被拦下，而不是留到执行器里才炸、且在快照里留下一条永远回不来的在飞记录。执行必须留在宿主，因为 Node 与 Workers 的执行方式不同（ADR-0003）。
- **为什么不给出口单独的类别**：它在邮箱、状态、推进之外没有行为差异，内核找不到任何区分它的规则。
- **为什么不兜底丢弃未识别类别**：静默丢弃会掩盖"消息被发到错误的节点"；入站形状归应用（ADR-0005），内核无从判断哪些该忽略。

## 代价（接受）

- 每条效果的结果都要一次全量快照写（出图一次、回执一次）。出口型动作也逃不掉："发出去了"本身是一个事实，回来一条 `result` 为空的 `@effect.end`。
- **图看不到增量**：节点无法对"模型正在吐字"做反应。真要，就用"每 N 段一个效果"在应用层做。
- 漏接回执没有任何告警，表现是与死锁无法区分的**静止**。
- 每个效果种类都要先在宿主里注册 schema 才能被节点使用；step 必须显式写 `default`，漏写会走到 TypeScript 穷尽检查或运行时错误，而不是被悄悄吃掉。
- 节点的 `state` 里必须自己记"我在等哪个 `correlationId`"，内核不代劳。

## Retired designs（不要重提）

- **`@effect.chunk` 与 `@effect.error` 两个信封**：增量取消，失败并入 `end`。
- **易失转移**（不落盘的推进）。
- **消息上的 `correlation`**：应答配对靠 `from`，应用自己的关联 id 放 `body`；效果侧用 `correlationId`（它只存在于效果请求与回执里，不在消息信封上，所以不是这条废弃设计）。
- **`onEffectEnd` 之类的"回执钩子"**。
- **术语"出口节点"**，以及任何让内核区分出口与非出口的规则。
- **内核对效果 kind 一无所知**：至少要认名字与 schema 才能拦下非法效果。
- **内核提供默认丢弃**未识别的消息类别。
- **Run 内 await effect**（效果结果回灌转移的返回值）。

## 反转条件

- 如果大量节点都在重复同一份"发 effect + 忽略回执"的样板，就在 agents 包里提供 helper，而不是把出口提成内核概念。
- 如果出现"节点必须对增量做决策"的真实需求（逐字审计、流式工具调用），chunk 会以**多段效果**的形态回到图里，而不是回到"易失通道"。
- 如果宿主确实无法旁路推（只有无状态的请求-响应，没有出网连接），观察面会回来要求内核承载增量。
