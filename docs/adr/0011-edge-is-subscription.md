# 边是订阅，投递是寻址

形状里的边是一条**订阅**：发送方只给出类别（端口），谁来接由形状决定——可以零个，也可以多个，**接了几个就是几条边，没有第二处声明**。发送时显式给出目标 id 是另一种投递：**寻址**，一对一，不经过边。而条件永远不是形状的事：分支、守卫、策略都写在节点的 `step` 里。

**Status**: accepted；取代 ADR-0002 的「扇出不在边层」与「`(from, port)` 至多一条边」，以及 ADR-0001 中「端口规则与节点相同：`(from, port)` 至多一条边」这一句。

## 决定

- **边仍是二元组** `{ from, to, port }`，`(from, port)` 可以有 0..N 条边。`edge_port_taken` 换成「完全重复的 `(from, port, to)` 报错」。
- **一个端口的基数就是边表里接了几条边。** 这是唯一的声明。`ports(config)` 仍然只声明 `{ 端口名: body schema }`（ADR-0004 不变），不额外声明「这个端口允许几个目标」——那会是对边表的第二次陈述，且可能与边表矛盾。「接了几个」是看一眼边表就知道的事实，不需要一个可能与它打架的标签。
- **两种投递，语义不同**：
  - **沿边发 = 订阅**。发送方只给类别。零个订阅者 → 丢弃并记 `dropped`（不变）；N 个订阅者 → N 条消息、N 个 `seq`。
  - **显式 `to` = 寻址**。目标唯一，不经过边；`port` 仍然必填、body 仍然按该端口的 schema 校验（ADR-0005 不变）。
- **一条 `send` 的多次投递是同一次提交**：同一个 `step` 产物、同一次转移、同一次存储事务（ADR-0013）。`snapshot_too_large` 在转移之后检查，所以要么全部入队、要么整条转移不应用（停住）——不存在「投了一半」。
- **触发器同构**：从触发器出发的边同样可以有多条。一个事件源要投多路，不必再开多个输出或多加转发节点。
- **端口名继续归发送方**：消息类别是内容的一部分——谁说的话，由谁定类别。不引入 topic / 订阅表 / 总线这类形状成员。
- **未接线的输出仍然丢弃并记日志**（ADR-0002 不变）。

## 为什么

- **为什么不再要求「写一个节点做 fork」**：ADR-0002 那句算的是「语义正确」的账，没算另一笔——每加一个结构点就要写一份节点定义（名字、版本、state schema、ports、step），以后还要迁移。编排是这份内核的核心用途时，后者是主账；而扇出在编排里是**结构**，不是行为。
- **为什么不需要第二处声明**：ADR-0002 唯一真正的损失是「一条指令被静默多播」。但那件事在形状里根本不静默——多播是**两行边**，可读、可 diff、在快照里。真正静默的只有「模板或 `graph.mutate` 加了第二条边」，而那两处都是作者自己写的代码。用 `mode: unicast | multicast` 去防它，等于引入一个内核无法验证的语义标签（内核不知道什么是指令），只为了换一个机械后果（拒绝第二条边）；而同样的检查，一条图 lint 免费就能给。**把「多播」变成需要显式许可的动作，方向与 ADR-0011 相反。**
- **为什么不是 topic / 总线**：语法上与「一条 `send` 多个目标」等价，但四点更差。
  1. **悬空成为常态**：名字独立于发送方，就允许「先有订阅、再有发布」，消息会落到没人订阅的名字上——而内核无法区分「作者故意没人订阅」与「作者忘了订阅」。ADR-0002 拒绝「投递无路报错」正是因为这个区别在运行时不存在。
  2. **可读性搬家**：图的全部价值是「一眼看出谁跟谁有关系」；topic 把它变成一次查询。
  3. **天然想跨工作流**：名字一旦全局，「一份工作流 = 一条快照」开始漏（ADR-0001 已把跨工作流投递划给宿主）。
  4. **原子性**：二元边一次提交即可；topic 要维护发布表与订阅表两个集合的一致性。
- **为什么条件仍然不进形状**：条件不是拓扑。边一旦带守卫，形状就成了程序，「这条边传的是什么」会同时依赖端口名与守卫，而形状校验只看得到前者——这正是 ADR-0005 拒绝「端口与类别分离」的同一条理由。同理，「这个端口是事实还是指令」是语义，不是拓扑。
- **为什么端口名不改为归订阅方**：那等于「名字先于发送方存在」，见上面第 1 点。

## 代价（接受）

- **形状不担保「一条指令只做一次」**。它担保的是「接了几个就投几个」，而接了几个写在边表里，可读、可 diff、可 review。内核不做语义担保——它无法判断一条消息是不是指令。
- **防「误接第二个目标」只能靠 lint 或 review**，没有声明期校验。这是接受 `mode` 被否决的直接代价。
- **`fork` 节点不再需要，但「需要顺序的分发」仍然需要节点**：顺序、失败、去重仍然是节点的事（ADR-0002 的语义理由仍成立，只是不再是唯一手段）。
- **中介节点仍不能原样转发**（ADR-0005）：fork / relay 只能用自己的端口发，类别会改名。
- **多播 + 共享下游 = 隐式无序 join**。这类图单目标时画不出来，现在画得出来，但它表达的是汇合，应该有显式的 `join` 节点。这是约定，不是校验——「下游是否汇合」是可达性分析，而边是运行时数据。

## Retired designs（不要重提）

- **边层扇出 retired**（ADR-0002 的那一节作废）。
- **`(from, port)` 至多一条边**、`edge_port_taken`。
- **端口基数声明（`mode: "unicast" | "multicast"`，或任何「一个端口最多接几个」的字段）**：边表已经是基数的唯一真源，再加一个可能与它矛盾的第二声明，换来的只是「作者没注意」这一个看得见的错误。要静态不变量的话，有价值的是**下界**（抓「忘了接线」），不是上界。
- **端口 + 订阅表 / 主题 / 总线** 作为形状的成员。
- **边上的守卫 / 条件投递**。
- **把「每个路由点都必须写一份节点定义」当作必然**（它现在只是可选手段）。
- **把多播当成「发送方决定扇出」**：扇出是形状的事（谁订阅），不是发送方的事。

## 反转条件

- 如果「忘了接线」成为真实痛点（`agent` 的 `reply` 端口没接上，工作流跑完什么也没发生，只在日志里留一条 `dropped`），加一个**下界**（`min: 1` 之类）——`min` 恰好能让「故意没人订阅」与「忘了订阅」区分开，而 ADR-0002 当初拒绝「投递无路报错」正是因为区分不了。**不要加上界**：上界就是边表。
- 如果多播成为默认、且下游频繁汇合，讨论把「汇合」提成形状成员，而不是让每个应用各写一个 `join`。
- 如果出现必须「原样转发」的通用中间件（代理、审计、录制回放），类别与端口名会重新分离（ADR-0005 的反转条件）。
