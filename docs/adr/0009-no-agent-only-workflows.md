# 没有 agent，只有工作流：问模型的是一种节点，循环是图结构

框架里只有**工作流**。一份工作流**可能**含有：问 LLM 的节点、能用 JSON 调用的工具、用户自己写的代码、做判断的预制节点、与外部对接的接口。传统意义上的 "agent"（对话 + 问模型 + 调工具，绕成一个环）只是这种工作流的**一种形状**，不是概念：内核不认识它，任何包里也没有一份叫 agent 的东西。"subagent" 同理，也不是概念；"用另一份上下文去问模型"怎么做，另写 ADR。

**Status**: accepted

## 决定

- **没有 agent / subagent 这两个概念**。术语表、包名、导出名、节点定义名里都不出现。经典的"对话 + 问模型 + 工具"只作为 examples 里的一份模板出现，是用法，不是类型。
- **跟问模型有关的东西都在 `@arbetslag/llm`**，和 Performer 放在一起（`@arbetslag/agents` 并进来，不再存在）。它们都建立在同一份 history 格式和工具协议上：
  - history 消息格式、`model.complete` 效果种类的声明（实现是 Performer 的事）。`timer.wait` 不在这里：效果种类由发出它的节点声明，这里没有节点发它；
  - 工具协议、给节点定义附工具的 helper、`defineTool` 便捷写法、接线 helper（见下）；
  - 三份普通节点定义，彼此平级：
    - **conversation**：持有对话历史（ADR-0010）。
    - **LLM 节点**（`llm`）：收到 history 快照就交出一个 `model.complete` 效果；回执回来后，要么沿 `reply` 回话，要么沿 `tool.<name>` 端口调用工具。私有状态只记"在等什么"和上次问模型时 history 有多长（ADR-0010）。
    - **inbox**：可选，让 LLM 节点一句一句地答（ADR-0010）。
  - 厂商翻译仍在子路径（如 `@arbetslag/llm/openai`），只用节点的人不必碰它。
- **和模型无关的通用预制节点**（判断、`join`、延迟之类）以后用到时再建包（如 `@arbetslag/nodes`），现在不建空包。
- **不需要库的**：用户自己的代码直接用内核的 `defineNode` 写；和外部对接，进来走监听器与触发器（ADR-0015），出去走效果加 Performer；监听器相关的匹配函数（如 `chatIs`）留在宿主包。
- **循环是图结构**：LLM 节点不在 `step` 里 await 模型或工具（ADR-0004）。模型调用是效果，回执回来才继续（ADR-0006）；工具结果沿回边回来。每次转移只做一步，所以每一步都能落盘、被观察、被重放（ADR-0007）。
- **工具 (Tool) 是节点提供的东西，不是一类节点**：一份工具就是节点定义上可选的一份描述加一份调用协议。任何节点定义，**提供了工具，就能被这样调用**；没提供就不能。没有"工具节点"这一类。
  - **描述**：名字、说明、input 的 JSON Schema。它是 config 的函数（与 `ports(config)` 同理），一份节点定义可以给出零到多份，每份对应它接受的一种调用。
  - **描述同时是承诺**：给出描述的节点承诺遵守调用协议。
    - 调用：调用方沿 `tool.<name>` 端口发一条消息，body 是调用块（`{ callId, name, input }`）。
    - 结果：节点沿 `tool.result` 端口回一条结果块，带回同一个 `callId`。失败也是结果（input 不合描述、执行出错，都回 `ok: false`）。
    - 节点在回结果之前可以做任何普通转移能做的事：交出效果、等回执、改图。所以有副作用的节点（联网、对接外部接口）只要提供工具，同样能被调用。
  - **描述挂在 `@arbetslag/llm` 这一层，内核不认识**：它提供一个 helper，把描述附到节点定义上（今天 `defineTool` 附的那份元数据，推广到任意节点定义）。内核的 `NodeDefinition` 不变。
  - **调用方不限于 LLM 节点**：LLM 节点是第一个用它的，用户代码节点、判断节点照样可以按这份协议去调。
  - **LLM 节点这一侧**：一次返回多个调用时，各发各的，`callId` 记进等待集合；集合空了才再问模型。
  - 仍提供一个便捷写法（今天的 `defineTool`），用"一个同步纯函数"直接写出一个提供工具的节点。它只是写法，不是另一类东西。
- **LLM 节点的端口是 config 的函数**：config 里有工具描述列表，每个工具一个 `tool.<name>` 端口，外加 `reply`、`history`、`append`、`tool.result`。
- **接线的 helper 在构建期抄描述**：提供一个 helper，按它做的事命名（不叫 agentLayout）。作者给出"LLM 节点 + 若干提供工具的节点实例（定义 + config）"，helper 用各自的 config 求出描述、抄进 LLM 节点的 config，同时生成"LLM 节点 → 该节点"与"该节点 → LLM 节点"两条边。没提供工具的节点交给它就报错。作者只写一遍名字。运行时新增工具也用同一个 helper，生成一个 `graph.mutate`。
- **`model.complete` 效果**：`input = { model, messages, tools, params? }`，`correlationId` 由 LLM 节点给；结果是 `{ ok: true, message }` 或 `{ ok: false, error }`。失败时由节点自己决定重试还是把错误当回复发出（ADR-0006）。厂商参数放 `params`，对节点不透明，由对应的 Performer 解释。
- **history 的消息格式归 `@arbetslag/llm`**，与厂商无关：role、文本块、工具调用块、工具结果块。翻译成某家 API 是 Performer 的事。
- **第一版不压缩 history**：撞上快照上限就停住，让它可见（ADR-0008）。

## 为什么

- **为什么不要 agent 这个概念**：
  - 它给一种形状起了一个类型的名字。有了名字，设计就会围着它转：该是节点还是工作流？subagent 要不要特殊？这些问题都是名字制造的。
  - 工作流本来就能装下问模型、调工具、写代码、做判断、对接外部这些东西，以任意方式组合。"agent" 只是其中一种组合，抬成概念会让别的组合显得是二等的。
  - 没有它，每样东西都按它做的事命名，读者看名字就知道它做什么。
- **为什么工具是一份可选描述，而不是一类节点**：
  - 能被调用的东西五花八门：纯函数、用户代码、预制判断、外部接口。把它们都塞进"工具节点"这一类，要么逼作者把已有节点改写一遍，要么再加一个只做转发的适配节点。
  - 但也不是"任意节点自动可调用"：被调用意味着要按 `callId` 回结果，一个不知道这份协议的节点被调用了只会让调用方永远等下去。有没有描述，就是"我是否遵守这份协议"的声明。
  - 描述是 config 的函数，因为同一份定义在不同 config 下能做的事不同（一个对接外部接口的节点，暴露哪些操作由 config 决定）。
- **为什么叫"工具"**：
  - 它就是厂商 API 里的 tool（名字 + 说明 + JSON Schema），模型看到的也正是这份东西，读者不需要学新词。
  - 要防的是"工具是一类节点"这层联想，而不是这个词。说法上固定为"节点**提供**工具"：一个节点可以提供零到多个工具，随 config 而变；被调用的是节点提供的某个工具，不是"一个工具节点"。
- **为什么循环是图结构**：在一次转移里 await 模型与工具，与"step 是同步纯函数"（ADR-0004）冲突。拆成一次一步，每一步都能落盘、被观察、被重放。
- **为什么端口是 config 的函数**：工具有几个是每份工作流各自的事；端口固定，就会逼出一个只做转发的分发节点，工具名也要写两遍。纯函数保持内核可校验。
- **为什么 helper 在构建期抄描述**：step 看不到别的节点的定义，给它加查询能力等于开一个"节点互相窥探"的口子（与 ADR-0004 相反）；让作者手写又会漂移。构建期是唯一同时看得到两边定义的时刻。
- **为什么不先做压缩**：压缩策略因应用而异，第一版定的默认很可能是错的；停住是显式失败，不会悄悄丢上下文。
- **为什么并进 `@arbetslag/llm`**：history 格式、工具协议、`llm` 节点和 Performer 互相依赖；分成两个包只是多一层依赖，而且"agents"这个包名本身就是那个被拿掉的概念。
- **为什么通用预制节点现在不建包**：一个都还不存在；先建包只会得到一个空壳和一个猜出来的边界。
- **为什么格式归 `@arbetslag/llm`**：内核不认识 LLM；history 直接用某家厂商的格式，换模型就变成迁移 state。

## 代价（接受）

- 没有一个现成的 "agent" 可以直接拿来用：作者要自己接 conversation、LLM 节点和工具，或者照抄 examples 里的模板。
- 工具描述在 LLM 节点的 config 里有一份拷贝；只要不绕过 helper 手改，两边不会漂移，但内核不检查一致性。
- 描述是承诺，但没人强制：一个给了描述却不回结果（或回错 `callId`）的节点，会让调用方一直等。LLM 节点这一侧只能靠超时兜（`timer.wait`），协议本身不由内核校验。
- 节点定义的端口声明依赖 config。
- 每新增一个厂商，Performer 要写一份 history 格式翻译。

## Retired designs（不要重提）

- **agent 是一个概念**：不论作为内核概念、节点定义还是工作流类型。
- **subagent 是一个概念**。
- **LLM 节点内部循环 / 在 step 里 await 模型或工具**。
- **沿端口向目标要 `describe()`**，以及 `ctx` 暴露"端口接的是谁的哪份定义"。
- **固定的单个 `tool` 端口加分发节点**。
- **"工具节点"作为一类专门的节点定义**；**任意节点不加声明就可被调用**。
- **把描述做成内核 `NodeDefinition` 的字段**：内核不认识 LLM，也不需要这份描述。
- **第一版内置的 history 压缩 / 自动截断**；**history 直接采用厂商格式**。

## 反转条件

- 如果停住长对话成为常态，在 `@arbetslag/llm` 里提供压缩节点或 helper，而不是改内核或让 LLM 节点内置。
- 如果厂商格式的差异大到翻译层失真，重新讨论 history 格式是否留出不透明的扩展块。
- 如果构建期抄描述在运行时频繁失配（工具升级后 LLM 节点的拷贝落后），再讨论让 config 引用工具定义的版本而不是拷贝内容。

- 如果出现不问模型的工具调用方（例如判断节点要调工具），把工具协议从 `@arbetslag/llm` 拆到一个不依赖模型的包里。

## 验收

1. 代码、术语表、导出名、节点定义名、包名里不再出现 `agent` / `subagent`（examples 里的模板名除外，也尽量按用途命名）。
2. `@arbetslag/agents` 并进 `@arbetslag/llm`；它导出 conversation、LLM 节点、inbox、给节点定义附工具的 helper、便捷写法（今天的 `defineTool`）、接线的 helper；agents 包现有的测试全部改名后照样通过。
3. 一份**不是**用便捷写法写的普通节点定义（会交出效果、等回执再回结果），提供一个工具之后被 LLM 节点调用，结果按 `callId` 回到 LLM 节点。
4. 把一个没提供工具的节点交给接线 helper，构建期就报错。
5. `CONTEXT.md` 删去 agent、subagent 两条，新增 LLM 节点，把「工具」改写成"节点提供的描述 + 调用协议"；ADR-0010 里的 agent 改成 LLM 节点。
