# 核心只承诺因果顺序，不承诺时序

内核承诺的确定性只有一层：**给定同一份快照与同一串外部输入，内核自己的推进是一个函数**。它保证一条消息不会被安排在它的因之前被处理（因果闭合），并保证同一份快照永远给出同一个顺序（可复现）。除此之外——效果什么时候被执行、结果是什么、几个效果谁先完成、外部世界看到什么顺序——一律不承诺，而且不可能承诺。

**Status**: accepted；修正 ADR-0003 中「step 是纯的、确定性的，所以一整段图内推进崩溃后可以原样重放」这条**论据**（决定不变），并精确化 ADR-0007 的「顺序由内核保证确定」（决定不变）。

## 决定

用四个词把混在一起的「确定性」分开（本 ADR 内部用词）：

| | 是什么 | 承诺吗 |
|---|---|---|
| **D1 推导确定** | 内核的推进：取哪条消息、分配什么 `seq`、投给谁、按什么顺序、校验、预算在哪一步耗尽、停在哪 | **承诺** |
| **D2 可重放** | 从日志重建同一份快照，而不重新执行 `step` | 不承诺；将来要做见下 |
| **D3 语义确定** | 同样的输入，外部世界看到同样的结果 | **不承诺，做不到**（有外部调用） |
| **D4 分支时序** | 互不因果的分支之间谁先 | **不承诺，也不需要** |

- **D1 的精确措辞**：给定（快照、注册表、注入的 `now` 与 `newEffectId`、以及每个 `step` 的**返回值**），内核的推进完全确定，且不读取任何其它隐藏状态。`step` 自己的返回值是否确定**不在承诺内**（ADR-0004 允许读时钟与随机）。
- **唯一的消息顺序**：`seq` 在**入队时**由内核分配，随快照持久，跨重启保持。
  - **投递顺序 = (`sends' 数组下标, 目标 id) 的字典序**：一次转移里第 i 条 `send` 投给多个目标时，按目标 id 升序依次取 `seq`；第 i 条的全部目标先于第 i+1 条。
  - **同一邮箱 FIFO**；**跨邮箱取最小的 `seq`**（ADR-0007 不变）。
  - **因果闭合**：一条消息不会被安排在「导致它被发出的那条消息」之前处理。
- **第二个顺序承诺（与消息无关）**：`graph.mutate` 一批操作按固定顺序应用（先全量校验，再 新增 → 断线 → 接线 → 回收）。它是「形状是集合而不是序列」的支点（ADR-0002）。
- **`inFlight` 里 `effect` 的先后不是契约**：它只是 `advance` 的副产品。**执行器不得依赖它**，它的数组序也不承诺跨版本稳定。
- **顺序若有语义，必须在图里表达**：串边 = 因果（内核承诺）；多播 + `join` = 并行（顺序无关）。没有第三条路。
- **D2 如果将来要做**：日志记 `step` 的**输出**（`state` / `sends` / `effects`），重放 = 重新应用输出，而不是重新执行 `step`。**不要为了「让重放可能」而去禁止时钟与随机。**

## 为什么

- **为什么必须承诺 D1，哪怕它换不到任何语义**：单写者的状态机必然按某个顺序处理消息——这个顺序不是可选项，是必然存在。不规定它，约束一点没减少（顺序照样存在、照样影响结果），只是它变成一个未文档化的变量：测试偶发失败、bug 不可复现，而「该期望什么」也说不出来。**把它写下来是唯一有收益的选项。**
- **D1 换到的不是语义，是四件可操作的事**：① 测试可以对整份快照断言（现有测试全建立在这上面）；② 崩溃后「同一份快照再跑一次」得到同一个悬垂态（唯一能诊断的入口）；③ 预算切点可复现（「再跑一次接着推」有确定起点）；④ 转移日志可 diff（否则它当不了调试工具）。终端用户看不到这些，但没有它们，「恢复、重试、排查、验收」全部失去定义。
- **为什么 D2 不靠 `step` 确定**：ADR-0004 已经允许读时钟与随机，这让 `step` 更好写；而重放只需要重放**输出**。ADR-0003 把 D2 建立在 `step` 确定性上，是**论据错误而不是设计错误**：修论据，不改 ADR-0004，也不给每个节点加「时间必须从消息里来」的负担。
- **为什么顺序必须规范化，而不是「书写顺序」**：形状是状态、状态是**集合**（ADR-0002）。数组的插入顺序会把这个集合偷偷变成序列：两张节点集与边集完全相同的快照（一张手写、一张经过几次 `connect` / `disconnect`）会给出不同的投递顺序。规范化之后，顺序只是快照的函数，与到达路径无关——`dump` / `diff` / 手工修复才说得通。`graph.mutate` 的固定应用顺序已经在做同一件事。
- **为什么一条 `send` 的 N 个目标之间没有语义顺序**：它们互不因果。任何顺序都因果一致，所以取最简单的那个。
- **为什么是「最小 `seq`」而不是别的规则**：它是因果序的规范形态。轮转、按节点优先这类规则可能让「被某条消息引起的消息」先于它被处理——那是**错误**，不是「另一种顺序」。
- **为什么执行器不得依赖 `inFlight` 顺序**：ADR-0006 明确允许执行器并发；依赖它会让「先发 log 再发 notify」这种假顺序长出来，而它在并发下必然偶发失败。

## 代价（接受）

- **承诺顺序会形成依赖面**：测试与作者会依赖 FIFO。缓解：语义顺序必须在图里表达，所以依赖面被限制在测试与日志里，不在图的语义里。
- **优先级 / 抢占不可能**。紧急消息不能插队；一个实时 bot 的回复会排在积压之后。要优先级只能「一个优先级一份工作流」。这是本 ADR 明确放弃的能力。
- **图内延迟 = Σ（每步的落盘）**。「一次转移只做一步」不是风格，是配套的设计哲学；需要「先做二十件小事再发一个请求」的编排，在这个系统里就是慢的。
- **推进内部的实现不自由**：凡是改动「邮箱的数据结构、节点状态的遍历、消息的出入队」的重构，都必须守住这条顺序。例如为消除 `advance` 里每步整份 `structuredClone` / `JSON.stringify` 的开销而改变遍历方式时，不能顺手改掉顺序。
- **没有第二种排序手段**：所有「我想要某种顺序」的诉求只能落到「多条 `send`」或「串边」。

## Retired designs（不要重提）

- **「顺序未定义 / 内核不保证」**（ADR-0007 的反向）。
- **为了让重放可能而禁止时钟与随机**（「确定性 step」）。
- **用 `step` 的确定性来支持可重放**。
- **执行器依赖 `inFlight` 顺序**，或把 `inFlight` 数组序当执行契约。
- **同一条 `send` 的目标之间按书写顺序投递**。
- **把 D3（外部结果确定）当成可以承诺的东西**。

## 反转条件

- 如果优先级 / 抢占成为真实需求：先做「一个工作流一份优先级」，再讨论把全序从「最小 `seq`」放宽成「带权重的因果序」——那会破坏本 ADR，需要新 ADR。
- 如果 D2 成为需求（审计、回放、跨版本对账）：按上面最后一条做命令日志，并新增 ADR。它的动机是「少落盘 / 可回放」，与 D1 无关。
- 如果「每邮箱序号 + 确定性轮转」成为必要（ADR-0007 的反转条件）：只有它仍然保持因果闭合时才可行，且要重写本 ADR 的顺序规格。
